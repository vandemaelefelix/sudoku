Chapter 3

The app and the game screen

This chapter opens the phone app. You learn what Expo and React Native are, how the screens connect, where each feature lives, and what happens behind one tap on a cell. You also meet the save system, the themes, the animations, the splash, the translations and the stats.

How to read this chapter Each core idea starts with a problem and an everyday picture. Then comes a diagram. Then the real files and functions. Click, step and play with the widgets. They run in your browser and mirror the real code. Where the docs and the code disagree, this chapter follows the code.

What the app is made of

The app is an iPhone game. The developer wrote it in TypeScript, not in Swift. Three tools make that possible: React Native, Expo and Expo Router.

The problem

A phone app needs buttons, lists, animations and the camera. Each phone system draws these in its own way. Writing the app twice, once for iOS and once for Android, doubles the work. A web page in a wrapper feels slow and not native.

Analogy: a stage play Think of a theatre. The script is the same every night. The actors are real people on a real stage. React is the script: it says what the scene looks like now. React Native is the stage crew: it turns the script into real iOS buttons and views. Expo is the theatre company: it ships the tools, the props box and the ticket office.

The three names

React Native

You write a screen as a function that returns a tree of View, Text and Pressable. React Native draws a real iOS view for each one. The app uses React Native 0.86 and React 19.2.

Expo

Expo is a set of tools and ready-made native modules around React Native. The app uses Expo SDK 57: expo-sqlite for data, expo-haptics for vibration, expo-localization for the language.

Expo Router

Expo Router maps files to screens. A file in mobile/src/app/ is a route. This is the same idea as the pages folder of a web framework (ADR-016).

Two rules from mobile/AGENTS.md
  • ios/ and android/ are generated (ADR-002). Nobody edits them. Native settings go in app.json and config plugins.
  • The app runs on Hermes, a small JavaScript engine. Hermes lacks some new methods: toSorted, toReversed, findLast, Object.groupBy. Sort a copy instead: [...items].sort(). The Jest tests run on Node, which has these methods, so a test can hide the crash.
Expo Go or a development build? Expo Go is a ready-made app that runs plain Expo projects. This app uses native modules that Expo Go does not have (Skia, the camera frame processor, the scanner). So the developer builds their own development build with just ios-dev <UDID>. The build is called "Sudoku Dev". A change to a native module needs a new build. A change to TypeScript only needs a reload.

The route map: how screens connect

The problem

An app has many screens. The player must move between them, and the back button must work. Someone has to keep the list of screens and the stack of open ones.

Analogy: a stack of cards A Stack works like a pile of cards on a table. Opening a screen puts a card on top. Back takes the top card away. Home is the bottom card and never leaves.

Expo Router builds the pile from the files in mobile/src/app/. The root file _layout.tsx holds one Stack. Every other file is one card. Click a screen in the map to read what it does.

Click a screen. Use Tab and Enter on a keyboard.

_layout.tsx: the root

It renders one Stack with headerShown: false. Each screen draws its own themed header (ADR-016). The layout also nests the providers that every screen needs. The next figure shows the order.

Home: app/index.tsx

The route file only returns <HomeScreen /> from src/home/. The screen shows the level buttons, Continue, and a small stats card. It asks puzzles.current() whether a game is in progress, each time it gets focus. A level button calls puzzleStart.newGame(level, () => router.push('/game')).

Continue and the other buttons use router.navigate, not push. A second tap then finds the open screen and does not open a copy. Two game screens for one game would both save, and the older one could overwrite newer moves.

Game: app/game.tsx

It renders PlayScreen from src/game/. The route has no param: no game goes into a URL. The screen reads the game in progress from the repository (ADR-016, point 3). Back calls router.dismissTo('/'). The game stays saved, so Continue resumes it.

Scan: app/scan.tsx

It renders ScanFlow from src/scan/: the camera, the correction screen and the start of a game. The hook useScannedStart calls puzzleStart.playScan(grid, () => router.replace('/game')). replace puts the game in the place of the scan, so Back from the game does not return to the camera. Chapter 4 explains the scan itself.

Stats: app/stats.tsx

It renders StatsScreen. The route gives it two extras: a refreshKey from useSync(), so the numbers read again after a sync wrote entries, and a footer with the sync line. The stats folder never imports the sync folder. The route joins them.

Settings: app/settings.tsx

It renders SettingsScreen with three callbacks: back, sign in and techniques. The screen holds the assists, the colourway, the appearance, the language, the haptics switch and the account section.

Techniques: app/techniques/index.tsx

A list of the solving techniques that the hints teach. A tap does router.push({ pathname: '/techniques/[technique]', params: { technique } }). Chapter 2 explains the techniques.

Technique page: app/techniques/[technique].tsx

The square brackets mark a dynamic route. The part in brackets is a param, and a param is a URL string. The route calls toTechniqueId(technique) to turn the string into a safe id. "Learn more" on the hint card opens this page over the game. The game stays mounted below, so the hint is still open after Back.

Sign in: app/sign-in.tsx

It renders SignInScreen from src/account/. The account is optional: the game works fully offline (SUD-01). Signing in only turns on the history sync (see chapter 6). When it is done, the route calls router.dismissTo('/settings').

Sign up: app/sign-up.tsx

The sign-in screen swaps to this one with router.replace('/sign-up'). replace puts the new card in the place of the old one, so Back does not return to Sign in.

Rule: a route file is thin (ADR-016) A file in src/app/ only renders one screen from a feature folder. It holds no logic, no state, no styles and no tests. A route param is a URL string. Data comes from a repository, never from a param.

The providers around every screen

A provider shares one thing with all the screens below it: the language, the theme switch, the account, the database. The root layout nests seven of them. The order has reasons.

Why does the order matter?
  • Language outside everything. Even the splash and the scan notices use catalogue text.
  • Splash overlay outside the storage. The overlay draws at once, before SQLite opens. A slow database open must never delay the first frame.
  • Theme transition outside the screens. The wave draws a picture over every screen, so it must wrap the stack.
  • Sync inside the storage. The sync reads and writes the history through the repositories. It renders the routes at once and works in the background.

The source is mobile/src/app/_layout.tsx. Its doc comment lists each reason with its ADR.

The feature folders and their boundaries

The problem

An app grows. If every file may import every other file, one change breaks ten places. Nobody can find anything. The rule must be simple enough that a tool can check it.

Analogy: a shopping mall Each shop (feature) has its own stock room. A shop does not walk into the stock room of the shop next door. If two shops need the same thing, it goes in the shared warehouse at the back: components/, hooks/, utils/.

All the app code lives in mobile/src/. The folders fall into four layers.

Inside a feature: one folder per kind of thing

Every feature uses the same layout. Create a folder only when it has a file.

Why this much structure? Pure logic in utils/ runs in a plain test with no React. That is why createGameSession and createPuzzleStart are normal functions, not hooks. The hook is a thin wrapper that connects the function to React. You will see this pattern again and again in this chapter.

How a game starts

The problem

Four places start a game: a level button on Home, a scan, "New puzzle" on the finish card and "Try this puzzle again" on the game-over sheet. If each place wrote its own code, they would drift apart. One would forget to ask before it throws away a game in progress. Another would start two games with a double tap.

Analogy: one ticket desk A cinema has one ticket desk. Every customer, whether they came by phone or at the door, goes through the same desk. The desk asks "do you want to leave your current film?" before it gives a new ticket. Only one customer is served at a time.

The desk is createPuzzleStart in mobile/src/game/utils/puzzleStart.utils.ts. It is plain TypeScript (no React). The hook usePuzzleStart hands it the repository, the owner and the "are you sure?" dialog.

The four ways in

newGame(level, opened). Called from Home.

  1. It asks first, when a game is in progress.
  2. newGeneratedGame(level, random) in newGame.utils.ts draws a seed below one million (SEED_COUNT), then calls the core generate(level, seed). The same seed always gives the same puzzle. The seed is the "puzzle number" on the finish card (ADR-011).
  3. The request is { level, source: 'generated', seed, game }.

The core builds the puzzle. See chapter 2.

playScan(grid, opened). Called from the scan flow after the correction screen.

  1. It asks first, as for a level.
  2. The level comes from scannedLevel(givens). It grades the puzzle with the core grade(). A grade of beyond becomes expert, so the four levels of the sync contract stay.
  3. The request has source: 'scanned' and seed: null. No seed exists for a paper puzzle.

The scanned level is an estimate, so a scanned game never counts for a best time (ADR-012, ADR-023).

newPuzzle(from). Called from the finish card and the game-over sheet.

It makes a new generated game at the level of the game that is over. It does not ask, because the game is over and there is nothing to lose. It uses ask: false.

retry(from). Called from "Try this puzzle again" on the game-over sheet.

It rebuilds the game from the same givens and solution, with startEntries as the entries. The result is a new game in progress with a new id and the same seed. The lost game stays in the history as one entry. It does not ask.

The new id matters. PlayScreen gives GameScreen key={progress.id}, so React unmounts the old session and mounts a fresh one.

The details of run()
  • The busy flag. start() discards the game before it. A second tap during the first start must not start a second game. While busy is true, run returns null.
  • Return values. Each start gives the new SavedProgress, or null. null means cancel, busy or failed. A failure writes a dev warning. The caller shows no error and keeps its screen.
  • peek() before current(). The question reads the stored state. peek() follows the last read, so the tap waits for no database read.
  • A failed navigation is not a failed start. opened() sits in its own try/catch. The game did start, so the promise still resolves.
  • Measures. startMeasures records the time from the tap (quality scenario QR-12). A start that gives no game clears its mark.

The game session: one tap, step by step

The problem

The game screen has 81 cells, a keypad, a timer and a hint card. They all show one game and they all change it. If each part kept its own copy, the copies would disagree. The rules also need tests, and a test should not need a phone.

Analogy: a bank counter The game is the account book. Nobody writes in it directly. A customer fills in a slip (an action). The clerk (the reducer) reads the slip, checks the rules and returns a new page of the book. Then a bell rings, and every screen that shows the balance looks again.

The idea has a name: a reducer. Three layers cooperate:

  1. The core rules in @sudoku/core (shared/core/src/game/actions.ts): select, place, toggleNote, erase, undo, pause, resume, tick. Each takes a Game and returns a new Game. No React, no clock, no I/O (SUD-04).
  2. The session in mobile/src/game/utils/session.utils.ts (reduceSession) wraps the game with the screen state: notes mode, the last move, the open hint.
  3. The session object in gameSession.utils.ts (createGameSession) adds the clock, the subscribers and the saves.

Follow one tap. The player taps cell 40, then presses the key 5.

1. The player taps cell 40

The cell calls actions.select(40). The actions object comes from useGameActions(). It is the same object for the whole game, so a cell never renders again because of it.

2. The action is a small object

select is a one-line function: dispatch({ type: 'select', cell }). An action says what happened, not how to handle it. The type SessionAction lists every action the player can do: select, digit, erase, undo, hint, the hint-card buttons, toggleNotesMode, pause, resume, and the clock's tick.

3. The reducer decides

dispatch calls reduceSession(session, action). A switch in step() picks the case. For select it calls the core select(game, cell). That function checks the range, returns the same game if the status is not playing or the cell is already selected, and otherwise returns { ...game, selected: cell }.

4. A new state, or the same one

withGame checks identity: if the core returned the same game, the session stays the same object, and dispatch stops here (if (session === previous) return). Otherwise the session is a new object. dispatch then calls syncClock() and asks needsSave(lastSaved, session.game). A selection is not a save trigger, so no write happens.

5. Everyone who listens renders again

dispatch calls every listener. React's useSyncExternalStore in useGameSession reads getSnapshot(), sees a new object and renders. GameProvider pushes the new state into context. The grid draws the selection tile on cell 40 and the assist shades. The clock tick later changes only the time context, so the 81 cells do not render each second.

6. The player presses 5

actions.digit(5) becomes { type: 'digit', digit: 5 }. In placeDigit: if notes mode is on, the key toggles a note. Otherwise the core place() runs. It copies the entries with the new digit, clears the notes of that cell, removes 5 from the notes of the peers in the row, column and box, and pushes an undo step. A wrong digit also raises mistakes. A Move record with id + 1 goes into the session, so the haptics and animations know a move happened.

7. The save

Now needsSave is true: entries changed. saveGame() calls the SaveGame function that the play screen gave. That function is the save queue. It returns at once and never throws, so the UI never waits for the database. The next section shows what the queue does.

Who holds what

The trick of board and game

The Session holds both game and board. A clock tick changes game.playedMs and makes a new game object. If the grid read game, it would render every second. So reduceSession keeps board pointing at the game of the last change other than time. After a tick, board is the same object. The doc comment on Session says so: board.playedMs is stale, read game.playedMs for the time.

The hook returns { state, playedMs, actions }. state is memoised on [board, notesMode, move, hint]. This keeps the grid from rendering on every clock tick.

Why useSyncExternalStore?

The session is a plain object outside React. It offers getSnapshot() and subscribe(listener). This is exactly the contract of useSyncExternalStore, the React hook for "state that lives outside". The snapshot must be the same object until something changes, so React can compare by identity. That is why every reducer step returns the same object when nothing changed.

    Input: digits, notes, undo and mistakes

    The problem

    A player does more than type a digit. They pencil in candidates, take a move back, clear a cell. And the game must punish a wrong digit, but not too hard. Each of these needs a rule. All rules must live in one place, so the screen can stay dumb.

    One keypad, two meanings

    The keypad has nine keys. What a key does depends on notes mode. In the session, notesMode is screen state, not a rule of the game. placeDigit in session.utils.ts reads it:

    ModeKey 5 callsMove kindHaptic
    Notes offplace(game, 5)number or cleartap
    Notes ontoggleNote(game, 5)notetick

    The Notes toggle only works while the game is playing. A pause or an end turns it into a no-op.

    What place() does, in order

    • A wrong digit stays in the cell. It shows with the conflict colour. The player can fix it, or leave it. Each new wrong digit adds a mistake. MAX_MISTAKES is 3. The third one sets status: 'lost'.
    • Entry check with the solution. The app knows the solution of every puzzle (the generator makes it, and a scan is verified to have exactly one). That is why a mistake is a fact, not an opinion.
    • A complete number is locked. When all nine copies of a digit are right, its key is disabled and faded. A wrong copy of a complete number can still be cleared with its own key.
    • Notes clean up after themselves. A placed digit removes itself from the notes of its peers (withNumber uses peersOf(cell) from the core).
    • Notes are sorted. toggleNote keeps them in order 1 to 9, so two games with the same notes are equal.

    Undo

    Every edit (place, toggleNote, erase, hint fill) calls withUndoStep(game). It pushes the old entries and notes onto undoSteps and keeps at most UNDO_LIMIT (100) steps. undo() pops the last step and restores both. It never changes the mistakes, the hints used, the selected cell or the time. So a player cannot undo a wrong digit to dodge the penalty.

    The UI asks "can I undo?" with canUndo(game): it runs undo(game) and checks whether the game object changed. The same idea is behind canErase. No extra flag exists to keep in sync.

    Why "same object means no change"? Every core action returns the same game when it does nothing. The session and the session object compare with ===. That one rule gives a cheap "did anything happen?" test for renders, saves, haptics and the can-undo button. It is the quiet backbone of the app.
    Not what you think: ADR-020 The name "full-cell input" can sound like a typing mode. It is not. ADR-020 says that the digit model reads the whole 64 x 64 cell image, with the grid lines still in it, not a cropped cell. That is part of the scan pipeline. See chapter 5 and chapter 4. In the game the player always types into one selected cell, and the keypad has no other input mode.

    Assists

    An assist only changes how the grid is drawn. It never changes the rules. There are four. All are on by default. mobile/src/game/constants/assists.constants.ts holds the type and the defaults.

    Assist keyShades
    rowColumnThe row and the column of the selected cell
    boxThe 3 x 3 box of the selected cell
    selectedCellThe selection tile on the selected cell
    sameNumbersEvery cell that holds the number of the selected cell

    The Settings screen shows a switch for each one, with a small live preview grid (AssistPreview). The four booleans are saved as one JSON text under the key game.assists (see the preferences section). parseAssists is forgiving: a missing or broken value gives the default, and an assist that a later version adds starts on.

    Each cell gets a CellView from cell.utils.ts: fill is one of plain, peer, same or conflict. A wrong entry keeps its conflict fill, whatever the assists say.

    A player presses Undo after a wrong digit. What happens to the three mistake dots?

    In the core, undo() restores only entries and notes. The mistakes, the hints used, the selected cell and the time stay.

    The timer and the pause

    The problem

    A timer looks simple. It is not. The app can go to the background in the middle of a second. iOS can freeze the JavaScript. The phone can be killed. The timer must still tell the truth, and the player must not lose time or gain time.

    Analogy: a chess clock A chess clock does not count while a player thinks about leaving. Pressing the button stops one side. Here the clock stops when the game is paused, when the game ends, and when the app leaves the screen.

    Who counts the time

    • The core never reads a clock (SUD-04). tick(game, elapsedMs) only adds the number the app gives it. It does nothing unless status === 'playing', or when the number is not finite or is not above zero.
    • The session measures. A setInterval fires every CLOCK_INTERVAL_MS (1000 ms). flushClock computes now - last and dispatches { type: 'tick', elapsedMs }.
    • The interval only runs while it should. syncClock() starts it when the session is attached and the status is playing. It stops it in every other case. The function runs after each dispatch.
    • One report counts at most MAX_ELAPSED_MS (2000 ms). iOS can freeze JavaScript before the pause on AppState arrives. The first report after the return would hold all the frozen time. The cap guards against that.

    The pause

    The player pauses by tapping the timer, which is also the pause button. The PauseLayer then covers the grid, hides every digit and note, and says "Tap to resume". A tap resumes with a soft haptic.

    When the app leaves the foreground, session.background() runs these steps in this order:

    1. It counts the time since the last clock report (flushClock).
    2. It pauses the game. The flush must come first: the core ignores a tick once the game is paused.
    3. It saves the paused game with the exact time played. This is one write.

    useGameSession adds the one AppState listener. The listener calls session.background() for every state that is not active. The cleanup of attach() does the same at the end: it flushes the last slice of time, saves once more if the game changed, and stops the clock (QR-11: a killed app resumes at the last move).

    Pitfall: the order If the session paused first and flushed after, the last seconds before the pause would be lost, because the core drops a tick for a paused game. The comment in the code says it: "The flush comes first".

    Game over and the finish card

    Two moments end a game. They look very different, and they save in the same way.

    The third mistake: game over

    1. The core sets status: 'lost'. The last haptic is error.
    2. The board stays visible for LOST_HOLD_MS (400 ms), so the player sees the digit that ended the game.
    3. The game over sheet rises from the bottom. It shows how many cells were right (rightCells) and the time played.
    4. Three buttons: Try this puzzle again (retry), New puzzle (newPuzzle), Back to home.

    The last number: finish

    1. The core sets status: 'won' and reports completed.grid = true.
    2. A solve pulse washes over the whole grid. A haptic success goes with it.
    3. useSolveDelay(won) waits until the pulse is over. With Reduce Motion on, it is true at once.
    4. The finish card shows. Its numbers come from finishView() in finish.utils.ts.

    What the finish card shows

    • The title "Solved · Medium", the time, the mistakes (for example 1 of 3) and the hints.
    • The best time of the level, and a New best badge when this game beat it.
    • A small copy of the solved grid, with the givens and the entries in two styles.
    • The source: "Scanned from paper", or the puzzle number (the seed, with spaces: formatPuzzleNumber).
    • The date, formatted by intl.formatDate with the language of the player.
    When is it a "New best"? finishView asks the core: countsForBestTime({ result: 'won', source, hintsUsed }). Only a won generated game without hints counts (ADR-012). Then newBest = counts && (bestBefore === null || playedMs < bestBefore). The first counted win at a level is always a new best.

    The card is built from one function that returns plain strings (FinishView), including a VoiceOver label of the whole card. That makes it easy to test. It also tilts a little with the phone, as the motion section explains.

    Where the "game over" screen moments differ from the core statuses

    The core knows four statuses: playing, paused, lost, won. The screen shows five moments: playing, paused, game over, solving and finished. "Solving" is the short wait for the solve pulse. "Finished" is the card. The concept page game-screen.md has a state diagram that includes them. These are screen moments, not rules.

    Saving: SQLite and the repositories

    The problem

    A phone app gets killed all the time. The player gets a call, swipes the app away, or the battery dies. The next start must show the same board, the same notes and the same time (quality scenario QR-11). The history of finished games must also last, because the stats read it.

    Analogy: a notebook with a librarian The database is a notebook. Screens never write in it themselves. A librarian (the repository) takes a request, writes it neatly and hands back the answer. If the notebook changes shape, only the librarian learns the new shape.

    The pieces

    • expo-sqlite is a real SQL database in a file on the phone (ADR-012). It works offline (SUD-01).
    • Repository interfaces in mobile/src/storage/: PuzzleRepository (the game in progress), HistoryRepository (the finished games), StatsRepository (numbers for the stats screen), SyncStateRepository (the sync cursor and waiting list). Screens use the interface, never SQL.
    • Two implementations of each. The SQLite one runs on the phone. An in-memory one (memoryStorage.ts) runs in fast tests. One contract test in storage/contract/ (describeGameStorage) runs against both. If they ever disagree, a test fails.
    • Numbered migrations. migrations.ts is a list of SQL texts. PRAGMA user_version holds the last one that ran. Append a migration, never edit a shipped one. An app that meets a newer database refuses to start with a RangeError.
    • Sync-ready rows. Each row has a UUID, created_at, updated_at and a soft-delete deleted_at, so a later merge between devices only adds rows (ADR-012, ADR-028).
    A name check: ADR-018 ADR-018 is called "one data folder, two tables". It is about the training data of the machine learning side (data/cells.csv and data/sudoku-photos.csv), not about the app database. The app database has the tables in the next figure. See chapter 5 for ADR-018. For the app, the decision is ADR-012 with its amendments, and ADR-023 and ADR-028.

    The tables

    A game moves from "in progress" to "history"

    PuzzleRepository hides the SQL behind five calls:

    CallWhat it does
    start({ level, source, seed, game, owner })Inserts a new game in progress. In the same transaction it soft-deletes the old one. If the old game had moves (hasMoves), a history entry with the result abandoned is written.
    current()The game in progress, or null. A saved game that does not load gives null and stays in the table.
    save(id, game, owner)Writes the whole game as JSON. When the game is won or lost, the same transaction soft-deletes the row and writes the history entry. It does nothing when id is not the game in progress.
    discard(id)Removes a game in progress.
    peek()The game as far as the repository knows, without a read. A screen draws it in its first frame.

    Snapshots, not moves. A save writes the whole game, with its undo steps, in one row (toSavedGame / fromSavedGame in the core). The history keeps only the result: the time, the mistakes and the hints. A leaderboard would need a move log, and ADR-023 point 7 says that needs a new ADR.

    The save queue: fast taps, few writes

    A fast player makes ten moves in a second. Writing ten times is wasteful and could reorder. createSaveQueue in saveQueue.utils.ts follows two rules: one write runs at a time, and while it runs, only the newest game waits.

    Why a finished game skips the queue. If the winning save waited, a "New puzzle" tap could run start() first. The repository would then record the finished game as abandoned. So status !== 'playing' sends at once, and the repository keeps the order of its own writes.

    useSaveQueue(id) builds the queue for the id of the current game. It reads the owner at the time of the write, not at the time of the move, so a sign-in in the middle does not leave an older waiting game behind. In a development build it logs the time and size of each save, and tags slow saves (more than 50 ms).

    Which changes trigger a save

    needsSave(previous, next) in savedGame.ts compares fields by identity. A table SAVE_TRIGGER: Record<keyof Game, boolean> lists every field of Game. selected and playedMs are false. All others are true. Because the record type needs every key, adding a new Game field makes the build fail until someone decides.

    The clock tick does not save: it would write every second. The time is saved with the next move, or when the app leaves the foreground (background()), or when the screen closes.

    Why does the Jest test run real SQL?

    In Jest the repositories run on the SQLite that Node has built in, through a small adapter (nodeDatabase.ts). The adapter copies the behaviour of expo-sqlite 57: WAL mode, no busy timeout, a second connection for an exclusive transaction. So the tests check the real SQL, the migrations and the transactions, not a mock. See ADR-012, amendment "the first tables", point 6.

    The player wins at 02:11. Which sentence is true?

    A finished game never waits (createSaveQueue), and PuzzleRepository.save does both writes in one transaction, with the same id.

    Preferences: settings that stick

    The problem

    Settings are small: a switch, a colour name, a language. They must be ready before the first frame, or the app would flash the wrong theme. They must also reach every screen at once when the player changes one.

    • SettingDefinition<T> has a key (saved text keeps this key forever, so an update keeps the player's choice), a parse that never throws and always gives a default, and a serialize.
    • createSettingStore (preferences/settingStore.ts) reads the saved value on the first get() with getSync. It is synchronous, so the first frame already has the value. A store that throws gives the default: the app must still start.
    • set(value) changes the value in memory and tells the listeners first, then saves. The screen does not wait for the database. trySet logs a failed save and keeps the value for this session.
    • Same text, no change. set compares the serialized texts. A value that serializes the same does nothing.
    • Hooks. useSettingValue(store) uses useSyncExternalStore, the same trick as the game session. useHaptics() gives { on, setOn, play }. play reads the switch at the moment of the haptic, so it keeps its identity.

    Theming: Unistyles, colourways and appearance

    The problem

    The app has three colourways and two looks, so six themes. Every button, cell and line must change colour when the player picks another one. If each component held its own colours, one new colourway would touch hundreds of files. And a colour with too little contrast is a bug, not a taste.

    Analogy: paint by number A paint-by-number picture says "area 7 is the sky". The paint set decides what colour "sky" is. Components say "I need the colors.accent". The theme is the paint set.

    Tokens, in three tiers (ADR-015)

    TierExampleWho reads it
    Primitive tokenaccent: '#1f3fd1' in a palette.tsOnly the folder of its own theme
    Semantic tokencolors.text, type.given, shape.radius.mdMost components
    Component tokencomponents.cell.selected, components.key.fillOne component only

    A theme is one typed object, Theme in theme.types.ts. TypeScript refuses a theme that lacks a token. A unit test (contrast.test.ts) checks every text pair of every theme for a WCAG AA contrast of 4.5 to 1. Only src/theme/ may hold a colour value. just lint refuses hex values, rgb() and hsl() elsewhere.

    How a component gets its colour

    Unistyles (react-native-unistyles 3) is the styling library. A *.styles.ts file looks like this: 

    export const styles = StyleSheet.create((theme) => ({
  key: { backgroundColor: theme.components.key.fill },
}))

    The function takes the theme. Unistyles binds each style to the theme on the native side. When the theme changes, the native layer updates the views. React does not render again. That is why the game grid "reads no theme hook" and a theme switch does not render it (ADR-015, ADR-031).

    Pitfall: do not spread a Unistyles style { ...styles.cell, left } loses the theme binding. Pass an array instead: [styles.cell, { left }]. A Skia canvas reads the theme with useUnistyles() and makes its paints again on a change, because Skia is not a style.

    Six themes from three palettes

    ADR-025 replaced the first four themes (Daylight, Midnight, Op-art, Progressive) with three colourways in the Op-art style: Cobalt, Forest and Bordeaux. ADR-026 added an appearance. A look is a colourway plus an appearance:

    • Light: a white page, coloured content.
    • Colour: the accent colour is the page. The content is white or light.
    • Auto: a preference, never a theme. A light iPhone gives Light. A dark iPhone gives Colour (resolveAppearance in theme/preference.ts).

    Each colourway is a folder in src/theme/themes/ with a palette.ts of about 14 values. One builder, buildOpartTheme, turns a palette into a full Theme. It runs twice: opart.light.ts and opart.colour.ts. The Colour look is derived from the accent: the page is the accent mixed with black by 0.16, and every other shade is the page with white laid over it (white(k)). Nobody writes the Colour values by hand.

    Unistyles registers six names: cobalt, forest, bordeaux and the same with -colour. Play with it. The board uses the real palette values from the repository.

    Colourway

    Appearance

    Resolved appearance:

    The board shows a selected given 7, its row, column and box (the peer fill), the other 7s (the same-number fill), a typed entry, and a conflict. In Colour the conflict is the peer fill with white stripes and a white digit, because red would not read on a coloured page (ADR-026).

    Rules that keep it consistent

    • Do not import the palette.ts of a theme from outside its folder. just lint checks this.
    • To add a colourway: add its name to ThemeName, add a folder, add one line to THEMES and one to COLOUR_THEMES (themes/registry.ts), add the two names to APP_THEMES (unistyles.ts) and one line to DECORATIONS. TypeScript names every place that misses it.
    • The saved preference is read before the first frame. unistyles.ts calls StyleSheet.configure with startupSettings(...), so Auto already knows the iPhone scheme.
    • The app is light only: userInterfaceStyle in app.json is light. Colour is a look of the app, not the iOS dark mode.
    • Theme decorations (the wavy Op-art bands on the correction panel, the finish card and the summary) live in a registry (theme/decorations/registry.ts), outside the theme object. A component renders <ThemeDecoration slot="panelEdge" />. An empty slot renders nothing.
    The theme switch wave (ADR-025, point 10)

    A change of the colourway or the appearance does not just snap. ThemeTransitionProvider takes a picture of the whole app with Skia makeImageFromView, draws it over every screen, then switches the theme under the picture. A wave of sudoku cells rises from the bottom row to the top row (700 ms). Each cell grows solid, erases its rectangle from the picture, and fades to show the live new theme. The cells are the splash cells (SplashCells) in the colours of the new theme, read from THEMES[next], because the effect draws before the switch is final.

    The wave waits until the screens have rendered the new theme (a Skia surface takes the new colours only in a render), at most 250 ms. The overlay takes no touch.

    ADR-031: display grids and fill colours

    The game grid cell reads no theme hook. Its fills come from Unistyles styles. But a small display grid, such as the assist preview, crossfades its fill layers. Those layers need plain colour values, so displayFill gives them from useUnistyles(). The values are the same tokens. The interactive grid does not change.

    The developer adds a fourth colourway, "Plum". Which file does a component need to change?

    Components read semantic tokens such as colors.accent. A new colourway is a new palette.ts, a builder call and a few registry lines.

    Motion: pulses, haptics and the card tilt

    The problem

    A game feels good when it answers your finger. A correct number should feel different from a wrong one. A finished row should feel like a small win. But motion costs battery, can make some players sick, and must never block play.

    Analogy: a drop in a pond A pulse is a ripple. The cell you touched is the drop. The ripple spreads cell by cell. Cells far away move later.

    Pulses

    A correct number can complete a row, a column, a box, all nine copies of a digit, or the whole grid. The core reports this in Completion ({ rows, columns, boxes, digits, grid }). The app turns it into delays:

    • pulsedCells(board, completed) collects the cells of every completed unit. For a digit it uses the solution, so a wrong copy never pulses.
    • pulseDelays(board, move, stepMs) gives each cell a delay of steps × stepMs. The steps are the Manhattan distance (rows plus columns) from the cell of the move. The longest way is 16 steps, from one corner to the other. A cell outside the pulse gets NO_PULSE (-1).
    • The look (stepMs, wave time, pop time, strength) comes from theme tokens (motion.pulseStep, components.pulse), so a colourway can tune it.

    Try it. Click a cell to choose the origin. Then pick what completed.

    Delays (ms)

    Click a cell.

    The number is the delay of each cell: distance from the origin × 45 ms. The real step comes from the theme token.

    Haptics: one move, one haptic

    hapticOf(move, lost) in useMoveHaptics.ts picks the strongest haptic that fits a move. It checks in this order, so two taps never blur:

    Check, in orderHapticiOS feedback
    A mistake. The third one ends the gamewarning, or error if lostnotification
    The grid is completesuccessnotification
    A row, column, box or digit completedthudmedium impact
    A normal numbertaplight impact
    A hint fillsoftsoft impact
    A note, a clear, an erase, an undotickselection

    useHaptics().play(name) checks the haptics switch in Settings. The hook useMoveHaptics runs an effect on the move record, which grows its id by one per move. That is how the same kind of move twice still plays twice. A phone without a haptic engine rejects the call, and playHaptic swallows the rejection.

    Reduce Motion When iOS "Reduce Motion" is on: fades stay, slides, scales and the shake go. No pulse animation plays, and the finish card shows at once. Haptics stay on, because Reduce Motion is not a haptics switch. Only the haptics switch in Settings turns them off (game-screen concept).

    Cell marks

    Some moves also mark the cell. mark.constants.ts holds the numbers: the mistake shake (steps of -3, 3, -2, 2, 0 points, 48 ms each), the hint glow (peak 0.35) and the undo flash (peak 0.22, quieter on purpose). A key that becomes complete grows 12 percent and fades (KEY_DONE, 500 ms). The grid also sweeps its digits in from the top left to the bottom right when it appears (useGridIntro, 28 ms per diagonal).

    The finish card tilts (ADR-017)

    The card reads the phone's rotation with Reanimated useAnimatedSensor(SensorType.ROTATION). The first reading is the rest position. The card then turns by the change from it. A change of TILT_RANGE = 0.35 radians tilts the card fully: MAX_ROTATE_X = 8 degrees and MAX_ROTATE_Y = 10 degrees, with a perspective of 900 points. A shine streak and a glare spot move with it. The glare moves 1.6 times as far (SPOT_PARALLAX) because it is the light itself. On iOS the device attitude needs no permission. With Reduce Motion on, the card does not read the sensor at all. tilt.utils.ts holds the math as a pure function, so a test checks it without a phone.

    The scan effects (ADR-014)

    The camera screen has its own animation engine. Each effect is a module with three worklets (create, step, draw). One engine, EffectCanvas, runs one frame callback and records one Skia picture per frame. A shader effect is a Skia runtime shader written in SkSL. In a development build, a pill on the camera screen switches effects at once. A release build runs only the default one. Chapter 4 shows where the effects sit in the scan.

    Pitfall: worklets capture early A worklet captures the values outside it when it is defined. A helper declared further down the file is still undefined inside the worklet. Put helpers and constants above the worklet. An imported value is always safe (mobile/AGENTS.md).

    The animated splash

    The problem

    iOS shows a launch screen while the app loads. That screen is a static picture. The app wants a short animation of its own, but the native layer cannot read the saved theme, and the first frame must match the native one, or the player sees a flash.

    Analogy: a curtain The native splash is a closed white curtain. The overlay is a second curtain in the same white, in front of it. The first one lifts unseen. The second then plays the show, and rises when the home screen is ready.

    The parts

    • SplashProvider owns the phase: intro, exit or done. It calls SplashScreen.preventAutoHideAsync() in the global scope to keep the native splash until the overlay is ready.
    • SplashRouteReady sits in the root layout. It calls useSplashReady(usePathname() !== '/'): the splash is "ready" as soon as the route is not Home, or when Home itself reports ready. A deep link that opens another screen first has no Home signal.
    • The exit starts when ready && introDone. A timer of MAX_WAIT_MS (3 s) calls markReady as a safety net. A stuck screen cannot hold the splash forever.
    • SplashOverlay has two parts: SplashWord (the six letters, in the title font of the saved theme, at twice the title size) and SplashCells (the wave, drawn with Skia). Its pointerEvents is none: touches fall through to the screen below.
    • The digits in the wave (29 percent of the cells) follow a valid sudoku pattern. A tiny joke for people who look closely.
    • Reduce Motion: the phase is done from the start. No overlay draws. The native splash hides when the home is ready.
    • The colours. The first frame of the overlay is white, like the native splash (ADR-025). It fades inside the 250 ms hold to the page colour of the saved look. After that, the word and cells use colors.text, colors.accent and colors.line of the saved theme.

    The same cells draw the wave of the theme switch. One component, two jobs.

    Why not a video or a Lottie file? The animation uses the same cell grid as the game, so it can follow every colourway and respond to Reduce Motion. A video would not change colour and would add weight to the app. The still icon is separate: it is cobalt in every colourway because an icon is a fixed image (ADR-025 point 9).

    Translations

    The problem

    The developer is from Flanders. The app should speak English and Dutch, and a third language should not need a rewrite. The hardest part is not the words. It is plurals ("1 hint", "2 hints"), dates, and the hint text that the sudoku engine writes.

    Analogy: a phrase book Code never says "Paused". It says "look up game.pause.title". Each language has its own phrase book. The book for the chosen language answers.

    How it holds together (ADR-033)

    • FormatJS (react-intl). Messages use ICU syntax, with {count, plural, one {#} other {#}} for plurals.
    • Typed ids. An id is <feature>.<part>.<name>, such as settings.language.title. An unknown id fails just typecheck. nl.ts has the type Record<MessageId, string>, so a missing Dutch message fails the build.
    • One word, one meaning, per language. The glossary is the English dictionary. nl.words.md is the Dutch one: Dutch of Flanders.
    • The language setting. app.language holds system, en or nl. system reads the iOS preferred languages with expo-localization and takes the first one the app has (resolveLocale). The formatting locale is the device tag when its language fits (nl-NL), else en-GB or nl-BE.
    • Hermes polyfills. i18n/polyfills.ts loads first (in mobile/index.ts). It adds Intl.Locale and PluralRules only when the runtime lacks them. The app uses no Intl API that Hermes lacks (RelativeTimeFormat, ListFormat, formatToParts). "5 min ago" is an ICU plural.
    • The engine writes ids, not text. The hint code in the core returns { id, values } from hintMessage(plan, step, rung). A value is a number or a typed part (a cell, a unit, a list of digits). The app formats each part from the catalogue. The core holds no player text, so it stays free of the app (SUD-04). A cell reads "row 4, column 9" or "rij 4, kolom 9", never "r4c9" (ADR-032). See chapter 2.
    • iOS texts (the camera permission text) cannot use react-intl. Expo locales in app.json gives a Dutch version.
    Lint rule: no literal text sudoku/no-literal-text in just lint refuses JSX text with letters, strings in label, title, accessibilityLabel, placeholder and Alert.alert. Log text, test ids and storage keys stay English. A util never calls useIntl: it gets a Formatter as a parameter (see finishView(intl, ...)). That is why utils stay pure and testable.

    Player stats and how they read the history

    The problem

    "My best Hard time", "my win rate", "my streak". These numbers come from the history of all finished games. Computing them in every screen would repeat SQL and would risk two screens that disagree.

    The rules (ADR-023)

    StatRule
    PlayedWon and lost games. An abandoned game is a separate count.
    Win rateWon divided by played. null when nothing was played.
    Best timeThe shortest time of a won generated game with no hints. The SQL: MIN(CASE WHEN result = 'won' AND hints_used = 0 AND source = 'generated' THEN played_ms END).
    Average timeThe mean of the same games. A level has an average only when it has a best time.
    Flawless winA won game with zero mistakes and zero hints.
    Day streakDays in a row with at least one win, in the time zone of the device. It stays alive until the end of the next day.
    Scanned gamesOff by default (includeScanned). A scanned level is an estimate. When on, they count in everything except the best and the average time.
    • Abandoned. A game is abandoned when a new game replaces it (see the persistence section). A game with no moves writes no entry: opening a puzzle and leaving does not count. hasMoves in the core says what a move is: an undo step, a mistake or a hint. Selecting a cell is not a move.
    • The filter. StatsFilter = { includeScanned, owner }. Only the entries of the owner count: a Clerk user ID, or null for games finished while signed out. Each device keeps its own stats after the sync (SUD-01).
    • Why the streak is in the core. SQLite has no time zones. computeStreak in @sudoku/core groups the win times by day. Every implementation, SQLite and in-memory, uses the same function.
    • One contract test. describeStats.testkit.ts is the one place that states the numbers for a known history. The SQLite repository and the in-memory fake both must pass it.
    • The stats refresh after a sync. The route app/stats.tsx passes refreshKey={revision} from useSync(). A new key makes useStats read again, so entries from another device show up. The sync is described in chapter 6.
    • Reset (development only). A "Reset stats" button shows when isDevelopmentVariant() is true. The production app has no way to delete the history.

    App variants (ADR-022)

    The developer has two copies of the app on the same iPhone: one to play, one to test. They must not share data or icons, and the developer must see which is which.

    Development

    • Name "Sudoku Dev"
    • Bundle id with .dev at the end
    • URL scheme sudoku-dev
    • Icons with a DEV ribbon
    • Effect lab pill, reset stats, measure logs
    • just ios-dev <UDID>

    Production

    • Name "Sudoku"
    • The plain bundle id
    • Release build
    • No lab, no reset
    • Backend values from PRODUCTION_BACKEND. With a null key, the account section and the sync are off
    • just ios-release <UDID>

    app.json holds the production config. app.config.ts reads the environment variable APP_VARIANT. Unset or empty means development. An unknown value stops the build. The app asks isDevelopmentVariant() (it reads Constants.expoConfig.extra.appVariant). The icons are drawn from one 100 x 100 design by just icons. Change the design in tools/icons/geometry.mjs, never in the PNGs.

    Why two different bundle ids? iOS treats an app with another bundle id as another app. So the development copy has its own database, its own settings and its own sign-in. A test build can never damage the games of the production copy.

    Recap

    Shape

    Expo and React Native run TypeScript. Routes are thin files. Features sit in their own folders and do not import each other.

    Game

    Core rules are pure. The session wraps them with notes mode, a clock and saves. React only listens through useSyncExternalStore.

    Data

    SQLite holds one game in progress and the history. Repositories hide the SQL. A save queue keeps writes few and in order.

    Look

    Tokens, not colours. Three palettes make six themes. A wave of cells switches theme.

    Feel

    One haptic per move. Pulses spread by distance. Reduce Motion drops the movement, not the haptics.

    Words

    Every text is an id in a catalogue. The engine returns ids with values. A lint rule enforces it.

    A new feature needs a function that both the home folder and the stats folder use. Where does it go?

    Features do not import sibling features (rule 9). Code that more than one feature uses moves to the shared folders. Copying would give two versions that drift apart.

    The app is in the background for 30 seconds while the player plays. Then iOS freezes JavaScript, and the app comes back. How much time does the first clock report add?

    background() flushes the time, pauses the game and saves. A paused game ignores ticks. The 2 second cap is a second guard for the case that JavaScript was frozen before the pause ran.
