Chapter 2

The sudoku engine

Inside shared/core lives a small TypeScript package that knows every rule of sudoku. It solves a puzzle, grades it, makes new ones, coaches the player with hints and keeps the score. It never touches the screen, the disk or the network. In this chapter you open it piece by piece.

How to read this chapter Each part starts with the problem. Then it gives an everyday picture, a diagram and the real code. Most diagrams react to clicks. Try them. The demos on this page run small copies of the real algorithms, so what you see is what the engine does.

1. What the engine is, and what it is not

A sudoku app has two kinds of code. One kind draws things: the grid, the keypad, the animations. The other kind knows things: is this digit allowed here, does this puzzle have one solution, which technique finds the next move. The second kind must give the same answer on every phone, every time. It must also be easy to test.

So the project keeps the second kind in its own package, @sudoku/core. Think of it as the referee of a chess club. The referee knows the rules and gives rulings. The referee never moves a piece and never owns a chessboard. The app (mobile/) owns the board and asks the referee.

Rule SUD-04 @sudoku/core must not depend on React Native, Expo or any I/O. A lint rule checks it in CI. The rule is in 00-DECISIONS.md and ADR-008.

What does "no I/O" mean in practice? Every function is pure: the same input gives the same output, and nothing else changes. Two examples show how far the project goes:

  • The engine never reads a clock. The function tick(game, elapsedMs) receives the time that passed. The app measures it.
  • The engine never calls Math.random(). It takes a seed and builds its own random stream. So a seed names one puzzle on every device.

Grid and units

The base of everything. types.ts says a grid is 81 numbers. units.ts lists the 27 rows, columns and boxes and the 20 peers of each cell. bits.ts counts set bits in a mask.

Solver and verify

solver.ts is a fast backtracking search that counts solutions: none, one or two or more. verify.ts uses it to judge a grid that a player or a scan filled.

Generator

generator.ts builds a full grid, removes clues while the puzzle keeps one solution, and keeps a puzzle only when it grades as the wanted level. random.ts holds the seeded random stream.

Technique solver

The folder technique/ solves like a person. It finds named moves such as a naked single or an X-wing. Each move is a Step. The grading and the hints both stand on it.

Grading

grading/grade.ts plays a puzzle through with the technique solver and turns what it needed into a level: easy, medium, hard or expert. The generator uses it to accept or reject puzzles. The app uses it to give a scanned puzzle a level.

Hints that teach

hint/plan.ts builds a short plan of steps from the player's board to one placed digit. The dashed arrow means that hints read the technique solver. The files message.ts and text.ts turn the plan into message ids. The app writes the words.

Game rules

game/ holds the Game value and the actions on it: select, place, note, erase, undo, pause, tick. Every action returns a new game. Nothing changes in place.

Stats

stats/ has two small rules: which finished games count for the best time, and how many days in a row the player won.

2. A grid is 81 numbers

The problem. A sudoku has 81 cells. The code must say "this cell", "the cells in the same row" and "the cells that block this digit" thousands of times per second. A slow or clumsy picture of the grid would make everything else slow or clumsy.

The picture. Think of the grid as a long row of 81 mailboxes, numbered from 0. A tall building and a long street hold the same mailboxes. Only the numbering decides who is your neighbour. The engine uses the street. It cuts the street into rows of nine.

In types.ts the whole idea is one line: type Grid = number[]. The array has 81 items, row by row. The value 0 means "empty". A digit is 1 to 9. createEmptyGrid() in grid.ts makes 81 zeros.

Units and peers

A unit is a group of nine cells that must hold the digits 1 to 9 exactly once. There are 27 units. The file units.ts lists them as arrays of cell numbers and gives them a number too:

Unit numbersKindConstantExample
0 to 8rowsROWSunit 0 = cells 0 to 8
9 to 17columnsCOLUMNSunit 9 = cells 0, 9, 18, … 72
18 to 26boxesBOXESunit 18 = cells 0, 1, 2, 9, 10, 11, 18, 19, 20

UNITS joins the three lists. UNITS_OF[cell] gives the three unit numbers of one cell. The peers of a cell are all other cells that share a unit with it. Count them: 8 in the row, 8 in the column and 4 more in the box (the other 4 box cells are already in the row or the column). That is 20. PEERS[cell] stores them, sorted.

Why precompute? The solver asks for the peers of a cell in its inner loop. Computing them each time would waste work. The engine builds PEERS and UNITS_OF when the module loads. After that, each question is an array read.

Try it. Move the mouse over the board, or click a cell to lock it. Switch between the row, the column, the box and all 20 peers.

A cell may hold a digit only if none of its peers holds it. That one idea drives the solver, the candidates and every technique.

Why a flat array and not an array of rows?

A flat array makes a cell one number. A cell number is easy to pass around, to store in a Set and to compare. A step of a technique, for example, lists its cells as plain numbers. A nested array would need a pair [row, column] everywhere.

The flat array also matches the other packages. The scanner, the saved game and the backend all send a grid as 81 numbers. They share the shape without sharing code.

Which cell number is in row 4, column 2? Count rows and columns from 0.

The cell number is row * 9 + column, so 4 * 9 + 2 = 38. The option 42 is row 4, column 6. The option 34 is row 3, column 7.

3. Candidates and bit sets

The problem. To solve a sudoku you ask one question again and again: which digits can still go in this cell? The answers are the candidates of the cell. A cell can hold a digit only if no peer holds it already.

The picture. Imagine a row of nine light switches on the wall of each cell, one for each digit. Switch on means "this digit is still possible". Every digit that a peer holds switches one light off. A cell with one light left has an answer. A cell with no light left means the board is broken.

A computer stores nine switches in one small number. This is a bit set, or mask. Digit d is the bit at place d − 1, counted from the right. So the mask 0b000010101 means "1, 3 and 5 are possible". The number is 21 in decimal, but nobody reads it that way.

In technique/candidates.ts, computeCandidates(board) makes an array of 81 masks (a Uint16Array). It starts with all nine bits on in every cell. Then, for each cell that holds a digit, it sets that cell's own mask to 0 and clears that digit's bit in all 20 peers. A placed cell always has the mask 0. The notes of the player never enter this function (ADR-032).

Try it. Click an empty cell. The panel shows which digits its row, column and box already use, and what is left.

Click an empty cell.

Blue squares are digits that a unit already holds. The green row is what is left: the candidates. The solver computes the same thing in its inner loop, with three small masks per unit.

Two bit conventions, and the bit tricks of the solver

You may meet two ways to number the bits. The technique code (technique/masks.ts) uses bit d − 1 for digit d, so a mask fits in 9 bits: ALL_DIGITS = 0b1_1111_1111. The backtracking solver (solver.ts) uses bit d itself, so its constant is 0b11_1111_1110 and bit 0 stays empty. Both work. The solver's choice saves one subtraction in the hot loop. Do not mix the two: a mask from one place is not valid in the other.

Three small tricks appear in the solver. They all work on the lowest set bit:

  • bitCount loops rest &= rest - 1. This clears the lowest set bit, so the loop runs once per set bit.
  • rest & -rest isolates the lowest set bit. The solver takes the candidates one by one with it.
  • 31 - Math.clz32(bit) turns a single bit back into the digit. clz32 counts the leading zeros of a 32-bit number.

4. Checking a full grid

The problem. Two places hand the engine a full grid and ask "is this right?". One is the player who finishes a game. The other is the scan screen: the camera read a paper puzzle, the player typed the missing digits, and the app must say whether the result is a valid solution.

verify.ts answers with verifyGrid(givens, entries). The word givens means the printed digits. The word entries means the digits that someone wrote in. The function trusts the givens and judges the entries. It returns one of three verdicts:

solved

No unit holds a digit twice. The grid is a valid sudoku.

wrong

The givens have exactly one solution, and some entries differ from it. The verdict lists the right digit for each such cell.

clash

Some cells share a digit in a unit, and the givens cannot tell which one is wrong. The verdict lists the clashing cells.

The helper duplicateCells walks the 27 units. In each unit it remembers the first cell of each digit. When it meets the digit again, it marks both cells. Then verifyGrid asks the solver about the givens alone. When there is exactly one solution, the engine can say which entries are wrong, so the verdict is wrong and carries a hints record from cell number to the right digit. When the givens have no solution or many solutions, the engine cannot judge the entries. It returns clash and the cells that clash.

The app calls this in mobile/src/scan/hooks/useVerify/useVerify.ts. During play, the game uses a simpler check: isWrong(game, cell) in game/completion.ts compares a cell with the stored solution. The next section shows where that solution comes from.

5. The backtracking solver

The problem. The engine needs a solver that never gets stuck and that can count: is there no solution, exactly one, or more than one? A puzzle with two solutions is a bad puzzle. A scanned puzzle with zero solutions means the camera misread a digit. Two parts need this answer: the generator (while it removes clues) and verifyGrid.

The picture. A maze with chalk. At every fork you pick a path and write a mark. At a dead end you walk back to the last fork and rub out your mark. You try the next path. The trick of this solver is how it picks the fork: it always goes to the fork with the fewest paths. Fewer paths mean fewer wrong turns.

This is the whole algorithm of solve(puzzle) in solver.ts:

  1. Check the input: 81 integers from 0 to 9. Else throw a RangeError.
  2. Fill three arrays of masks, rows, cols and boxes. Each mask holds the digits that the unit already uses. If a given clashes with an earlier one, return { count: 0 } at once.
  3. Search. Scan all empty cells. For each one, the candidate mask is ALL_DIGITS & ~(row | col | box). Remember the cell with the fewest candidates. Stop the scan early when a cell has 1 or 0.
  4. No empty cell left? That is a solution. Count it. Copy the grid when it is the first.
  5. The best cell has 0 candidates? Dead end. Return and let the caller try the next digit.
  6. Otherwise try each candidate: write it into the cell and into the three masks, call the search again, then undo the write.
  7. Stop only when the second solution appears. The result is { count: 0 }, { count: 1, solution } or { count: 2 }. The type comment says "count 2 means two or more".
Why the cell with the fewest candidates? A cell with one candidate is forced: no guess is needed. A cell with zero candidates ends the branch at once. Picking these first shrinks the tree a lot. Many puzzles finish without one dead end. A cell-by-cell scan from the top-left would try far more wrong digits.

Watch it work. This is a real expert puzzle with 25 givens. The page runs the same search as solver.ts, but it records each event so you can step through. Bold digits are the givens. Blue digits are guesses. The orange cell is the cell the solver just picked.

    Rows and columns in the log count from 1, as the app does. In code the cell numbers count from 0.

    Why the solver counts to two, and not to the end

    The answer "how many solutions" has only three useful values: none, one, or more than one. Once the search finds two, the exact number does not matter. Stopping there makes a bad puzzle cheap to reject. That is why search() returns true ("stop everything") when count >= 2, and why the result type has { count: 2 } with no list.

    The generator does not even call solve() for every clue it removes. It has a special search, createOtherSolutionSearch, that asks a narrower question: "if this one cell could not hold its old digit, would the puzzle still have a solution?" The old solution is known, so one found solution means "not unique". This is faster and it allocates nothing per call. A test proves that both give the same result.

    The solver finds a solution. Why does it keep searching?

    The solution is correct by construction: every digit was checked against the three masks. The search goes on because "unique" means "no other solution". If a second one appears, the result is { count: 2 } and the puzzle is not unique.

    6. The technique solver: solving like a person

    The problem. The backtracking solver is fast, but it is a poor teacher. If a hint said "try a 7 and see if it breaks", nobody would learn anything. And it cannot measure difficulty: a puzzle that takes the search a millisecond may still be hard for a human. The project needs a second solver that thinks the way a player thinks.

    The picture. Backtracking is like shaking a locked box until it opens. A technique is like reading the marks on the lock. It tells you why a pin must move. The technique solver only makes a move when it can name the reason.

    What a technique is

    A technique is a rule with a name. Using it once gives a step. A step does one of two things:

    • It places a digit: "this cell must hold a 6".
    • It eliminates candidates: "this cell cannot hold a 5". This opens no cell yet, but it makes a later step possible.

    The type Step in technique/types.ts is the data contract between the solver, the grading, the hints and the app. Click a field to see what it holds.

    Click a field to read about it.

    technique

    The id of the rule, such as 'nakedSingle' or 'xWing'. It is a string union of 23 ids. The grading and the hint text look the rule up by this id.

    placements

    The digits that the step puts on the board, as { cell, digit } pairs. The singles have one. Other techniques have none.

    eliminations

    The candidates that the step removes, as { cell, digit } pairs. A pointing step might remove a 5 from three cells.

    units

    The rows, columns or boxes that matter, as unit numbers 0 to 26. The first one is the focus unit: the place where the app tells the player to look.

    pattern

    The cells that form the technique itself: the two cells of a naked pair, the four corners of an X-wing.

    support

    Cells that already hold a digit on the board and cause the step. In a hidden single, the support cells are the placed digits that block the other cells of the unit.

    digits

    The digits of the pattern: the 3 and the 7 of a naked pair, or the single digit of a fish.

    links and groups

    Only for the chain techniques (links: the chain from cell to cell) and simple colouring (groups: the two colours). Every other step leaves them out.

    The loop: nextSteps and playThrough

    Two functions drive the folder. nextSteps(candidates, board, ranks) in technique/nextSteps.ts finds the next steps. playThrough(givens) in technique/playThrough.ts calls it in a loop until the puzzle is solved or stuck. Step through the loop:

    1. Start with a board

    The board is the givens at first. Later it also holds every digit that earlier steps placed.

    2. Compute the candidates

    computeCandidates gives one mask per cell. playThrough also clears the bits that earlier steps eliminated. They are stored in a struck array, because the board alone cannot show an elimination.

    3. Try the ranks, easiest first

    A rank is one line of TECHNIQUE_ORDER: a technique and its weight. The function findSteps sends each rank to its finder, for example findNakedSingles.

    4. The first rank with a result wins

    nextSteps returns every step of that one rank, sorted by focus unit, first pattern cell and first digit. The sort makes the result the same every time.

    5. Apply the first step, then loop

    Placements go on the board. Eliminations go into struck. Then the loop starts again from step 2.

    6. The end

    When no rank finds anything, playThrough returns what it has: the steps, the position before each step and a flag solved. A board with no empty cell is solved.

    How a finder works: the hidden single in code

    findHiddenSingles(candidates, board, kinds) in singles.ts does this:

    1. It walks the units of the wanted kinds: boxes first for the cheap rank, then rows and columns.
    2. For each digit 1 to 9, it skips the unit if the digit is already placed there.
    3. It collects the cells of the unit whose mask has the digit's bit.
    4. When exactly one cell is left, it builds a step with that placement.
    5. It stores a key (cell * 10 + digit) so that a digit that is hidden in two units gives one step only.
    6. For the support, it asks each other empty cell of the unit for its blockerOf: the peer with the lowest cell number that holds the digit.

    The fixed choice in the last point matters. When several peers hold the digit, the code always picks the lowest. The output never changes between two runs, so Vitest can pin a hint to the exact cells.

    The harder families, in a few words
    • Subsets (subsets.ts): naked and hidden pairs, triples and quads. The code tries every combination of 2, 3 or 4 cells (or digits) in a unit. It rejects a combination that has a smaller group inside it, so a triple never repeats a pair.
    • Fish (fish.ts): X-wing, swordfish, jellyfish. A fish of size n uses n base lines and n cover lines. The code runs once with rows as base lines and once with columns.
    • Single-digit patterns (singleDigit.ts): skyscraper and two-string kite. Both link two "strong links" of one digit.
    • Wings (wings.ts): XY, XYZ and W. They use cells with two or three candidates.
    • Unique rectangle (rectangles.ts): the only rank with needsUnique: true. It is wrong for a puzzle with two solutions, so nextSteps skips it unless the caller passes { unique: true }.
    • Colouring and chains (colouring.ts, chains.ts): the most powerful and the slowest. Their steps carry groups and links.

    The developer wrote all of them clean-room: the logic comes from reading HoDoKu and SudokuWiki, and the code copies nothing (ADR-032, point 15).

    7. Grading: how hard is this puzzle?

    The problem. The app offers four levels: easy, medium, hard and expert. "Hard" must mean the same for every puzzle. Counting clues is a poor measure: a puzzle with 30 clues can be a stroll or a wall. What makes a puzzle hard is the reasoning that a person needs.

    The picture. Think of a climbing route. Its grade is the hardest single move on it, not the number of handholds. The engine plays the puzzle through with the technique solver and looks at the hardest technique it needed.

    The function is grade(givens) in grading/grade.ts. It needs a puzzle with exactly one solution. It returns a Grade:

    FieldMeaning
    leveleasy, medium, hard, expert, or beyond when the technique solver does not finish. beyond is not a level of the game.
    hardestThe hardest technique used. First by level, then by weight inside a level.
    scoreThe sum of the weights of all steps, in Sudoku Explainer points.
    choiceA measure of how many moves a player can pick from. Explained below.
    stepsThe number of steps the solve took.

    The level ladder

    The map TECHNIQUE_LEVEL in grading/levels.ts gives each technique a level. The level of a puzzle is the level of its hardest technique. It is a Record over all technique ids, so adding a new technique id fails the typecheck until someone gives it a level. Click a step of the ladder.

    Click a step to read about it.

    Easy

    Full house, hidden single, naked single. A puzzle is easy when it needs only singles and its choice is 19 or more. The generator removes clues down to a floor of 40 givens.

    Medium

    Pointing, box-line, naked and hidden pairs and triples. A puzzle that needs only singles, but with a choice below 19, is medium too. The floor is 34 givens. About 91 in 100 attempts at 34 givens are medium.

    Hard

    X-wing, swordfish, jellyfish, skyscraper, two-string kite, the three wings, naked and hidden quads. The floor is 29 givens. About 9 in 100 attempts give a hard puzzle.

    Expert

    Unique rectangle, simple colouring, X-chain and XY-chain. The floor is 25 givens. Only about 8 in 100 attempts give an expert puzzle, so the generator may need a dozen attempts.

    Why there is a second order: GRADE_ORDER

    TECHNIQUE_ORDER puts the X-wing (hard) before the hidden pair (medium), because that is how people find them. If grading used that order, a puzzle that medium techniques can solve might use an X-wing on the way and grade as hard. That would be unfair.

    So levels.ts builds GRADE_ORDER: all easy ranks first, then all medium ranks, then hard, then expert. Inside a level it keeps the order of TECHNIQUE_ORDER. A harder technique now runs only when no easier level helps. The grade then shows the true minimum of what the puzzle needs.

    The choice: the same techniques can feel different

    Here is a surprise. Look at two real puzzles from the demo above. Both need only singles. But one is easy and one is medium. How?

    The difference is the choice. At each point of the solve, how many cells can a player fill right now with a single? When many cells are open at once, the puzzle is generous: any move works, the player never hunts. When only one cell is open at each point, the player must search for it. That feels harder, even though the technique is the same.

    The rule: a puzzle that needs only singles is easy when its choice is at least EASY_MIN_CHOICE = 19, and medium when it is lower. The value 19 comes from measuring 10 000 puzzles. The data is in the grading research record.

    How choiceOf counts

    The function plays the puzzle in rounds, and it measures only the first CHOICE_MOVES = 25 moves.

    1. A round fills every cell that a single can fill, all at once.
    2. It counts one move per cell. The value of each move is the number of cells in the round.
    3. When no single applies, it applies the first step of GRADE_ORDER and counts one move with the value 0.
    4. The choice is the mean value of the moves.

    A test example: a round that fills 2 cells counts two moves of value 2, so the choice is 2. A grid with a whole empty row has one round of 9 cells: nine moves of value 9, so the choice is 9. Because rounds do not depend on the scan order, the choice stays the same when a puzzle is rotated, transposed or relabelled. grading/symmetry.ts provides those transforms for the tests.

    gradesAs: a faster question for the generator

    The generator asks one question many times: "does this puzzle grade as hard?" It does not need the full grade. gradesAs(givens, level) runs the solver with the ranks up to the wanted level only. If it needs a harder rank, it stops with false at once. It also skips the choice unless the hardest technique is a single. A test proves that it always agrees with grade().

    The app also uses grade() on scanned puzzles, in mobile/src/game/utils/newGame.utils.ts. A scanned puzzle never counts for the best time, because its level is an estimate (ADR-011).

    A puzzle needs only naked singles and hidden singles. At every point, only one or two cells can be filled. What level does the engine give it?

    Singles solve it, so it is not beyond, and it is not hard. But a low choice makes it feel harder than an easy puzzle. levelOf in grade.ts turns an "easy" technique level into medium when the choice is below EASY_MIN_CHOICE.

    8. The generator: making a puzzle with one solution

    The problem. The app wants endless puzzles. Each needs exactly one solution and the level that the player chose. And a puzzle must be reproducible: when a friend types the same puzzle number, they must get the same board. The engine must do all this on a phone, in a blink.

    The picture. A sculptor starts with a full block of stone and chips pieces away. After each chip, the sculptor checks: can I still see only one statue? If a chip would let a second statue hide in the stone, the chip goes back. At the end, a judge looks at the statue and decides the level. A statue of the wrong level goes back to the block, and the sculptor starts again.

    The seed: one number names one puzzle

    random.ts holds createRandom(seed). It is Mulberry32, a tiny random number generator. A seed in, a stream of numbers in [0, 1) out. The same seed gives the same stream on every device and every JavaScript engine. That is why the finish card can say "Puzzle 412 077": the seed is the number. The app draws seeds below one million, but generate() accepts any integer up to 0xffffffff.

    The second helper is shuffled(items, random), a Fisher–Yates shuffle on a copy. Everything that looks random in the generator (the digit order, the clue order) goes through these two functions. Nothing calls Math.random().

    The pipeline

    1. A seed starts one random stream

    generate(level, seed) checks the arguments. It throws a RangeError for an unknown level or a seed that is not an integer from 0 to 0xffffffff. Then generateAtLevel makes one stream with createRandom(seed). All attempts share it.

    2. Build a full, valid grid

    fullGrid(random) fills the cells 0 to 80 in order. For each cell it tries the digits in a shuffled order and skips any that the row, column or box holds. When a later cell has no digit left, it backtracks. The finished grid is the solution.

    3. Remove clues, but keep one solution

    removeGivens shuffles the 81 cells. For each cell it empties it, then asks: could another digit fit here and still give a valid grid? If yes, the clue goes back. If no, it stays removed. The removal stops at the givens floor of the level, or when the list ends.

    4. Ask a judge

    gradesAs(givens, level) plays the puzzle through with the technique solver, only up to the wanted level. It is true when the grade equals the level.

    5. Keep it, or try again

    A match returns a Puzzle: { level, seed, givens, solution }. A miss draws the next full grid from the same stream. The stream has moved on, so the next grid is new. The loop runs at most MAX_ATTEMPTS = 250 times.

    6. The fallback

    If every attempt misses, the generator grades them and picks the one nearest to the wanted level. At the same distance, a level below wins: a puzzle that is too easy is safer than one that is too hard. If every attempt is beyond, it reveals clues until the solver can finish. The result is never beyond, and it is still the same on every device.

    The floor does not set the level Older versions picked the level by the number of clues (easy 40, medium 34, hard 29, expert 25). That was a poor measure of difficulty. Now those numbers are only a floor: the point where the removal stops. The grade decides the level. A hard puzzle may keep more than 29 clues when the removal cannot go lower. It is still a valid hard puzzle (ADR-011, amendment "generation by technique").
    LevelGivens floorShare of attempts that matchAttempts per puzzle
    easy4053 %1.9
    medium3491 %1.1
    hard298.6 %11.6
    expert257.8 %12.8

    The numbers come from ADR-011. The floor with the lowest expected time per puzzle won. A puzzle takes about one millisecond for easy and medium, and about 10 to 30 ms for hard and expert on a Mac. The chance that all 250 attempts miss for expert is about 1.5 in a billion.

      9. Hints that teach

      The problem. A hint that only shows a digit teaches nothing. The player gets the answer and learns nothing for the next puzzle. The project wants a coach: first "where to look", then "what technique", then "why", and the digit last. The player may stop at any point and finish alone. ADR-032 records the decision, and the hints concept describes it.

      The picture. A good teacher at your shoulder. First the teacher points at a row. Then names the trick. Then explains it. Only when you ask again, the teacher says the digit.

      Four rungs for each step

      RungThe card saysCosts a hint?
      1 LookWhere to look: "Look at row 8."No
      2 TechniqueThe name and a one-line definitionNo
      3 WhyOne or two sentences of reasoningNo
      4 Answer"Put 5 in row 8, column 7." Or "Remove 5 from column 8."Yes, when it shows a placement

      A hint is a plan

      Sometimes the next digit has no direct technique. The 5 may only appear after another step removes a candidate. So a hint is not one step but a hint plan: a short list of steps that ends in a placed digit. planHint(game) in hint/plan.ts builds it. The result has one of three shapes (the type HintPlan in hint/types.ts):

      • mistake: the board holds a wrong entry. The card says "Erase it first". This hint does not count.
      • steps: 1 to 6 steps. Only the last one places a digit. Its answer is that placement.
      • fallback: no hint technique reaches a placement in 6 steps. The answer is the empty cell with the fewest candidates.

      Three design choices that matter

      1. The candidates ignore the player's notes. planHint calls computeCandidates on the givens and the entries only. A player's notes may be wrong. The hint must not copy a wrong note (ADR-032, point 2).
      2. The choice is the same every time. Among steps of the same rank, byChoice prefers a step that places a digit, then the step nearest to the selected cell, then the lowest unit, pattern cell and digit. So the same board and selection always give the same plan. Vitest can pin it.
      3. Pruning keeps the plan honest. The greedy search may take an elimination that the final placement does not need. pruned() tries to drop each step and calls replays() to check that the remaining steps still work. Only needed steps stay.
      The engine holds no player text hintMessage(plan, stepIndex, rung) in hint/text.ts returns a message id with values, such as hint.pointing.why with a digit and two units. The app turns it into English or Dutch from mobile/src/i18n/messages/en.ts (ADR-033). Cells and units are indexes in the message. The app writes "row 8, column 7". This keeps the engine free of language, and the typecheck of the app proves that it has a text for every id.

      When does a hint count?

      Rungs 1 to 3 are free. A hint counts when the answer shows: the player taps "Fill it", taps "Show answer", or sees the fallback. The function revealHint(game, answer, shown) in game/actions.ts adds 1 to hintsUsed. The same answer counts once in a game session, so a second look adds nothing. fillHint places the answer, selects its cell and counts as revealHint does. A hint is never a mistake.

      A player opens a hint, reads rungs 1, 2 and 3, and then closes the card. They find the digit alone. How many hints does the game count?

      A hint counts when its answer shows. Rungs 1 to 3 never show the placement, so they are free. The player can still win a flawless game and a best time. countsForBestTime needs hintsUsed === 0.

      10. The game and the stats

      The last two folders are small. They are still a good lesson in how to write rule code.

      The Game value

      game/types.ts defines Game: the grids givens, solution and entries; the pencil notes for each cell; the selected cell; the counters mistakes, hintsUsed and playedMs; a status; and the undoSteps. Everything is readonly. An action never changes a game. It returns a new one. That makes undo cheap (keep the old value) and makes the React screen simple (a new value means a new render).

      createGame({ givens, solution, entries }) checks that the grids fit together. A given must equal the solution, and a cell may not hold both a given and an entry. It throws a RangeError when they do not. If the entries already solve the grid, the game starts as won.

      The actions

      ActionWhat it does, and the rules inside
      selectMarks a cell. Throws for a number outside 0 to 80.
      placeWrites a digit. It clears the notes of that cell and removes the digit from the notes of the 20 peers. A wrong digit adds a mistake, and the third mistake sets lost (MAX_MISTAKES = 3). The last right digit sets won. The same digit again erases the cell.
      toggleNoteAdds or removes one pencil mark in an empty cell.
      eraseClears the entry and the notes of the selected cell.
      undoRestores the entries and the notes of the last step (UNDO_LIMIT = 100 steps). It never gives back a mistake, a hint or time.
      pause, resumeSwitch between playing and paused.
      tickAdds the milliseconds that the app measured. The engine never reads a clock (SUD-04).
      revealHint, fillHintCount and place a hint. See the section on hints.

      Every action that changes a cell goes through the helper editableCell. It returns a cell only when the game is playing, a cell is selected and that cell is not a given. Else the action returns the same game object, so the screen can tell that nothing changed.

      What a move completed

      place returns a MoveResult: the new game and a Completion with the rows, columns, boxes and digits that the move finished, and whether the whole grid is done. completedBetween(before, after) in game/completion.ts computes it by comparing the two games. The game screen uses it to play the small pulse animations. The engine only reports facts. The app decides how they look.

      The stats rules

      The stats folder holds two rules. A third rule, the clock format, lives in game/. The history lives in a database in the app (SQLite). The database does the counting. The engine only keeps the rules that must be the same everywhere (ADR-023).

      • countsForBestTime(game) in stats/bestTime.ts: a game counts when it was won, generated (not scanned) and used no hints. A scanned puzzle has only an estimated level. The SQL in the app repeats this rule for speed. A contract test keeps the two the same.
      • formatClock(ms) in game/clock.ts gives "04:12". It rounds down to whole seconds, as the timer does, so the finish card and the stats screen show the same time. There are no hours: 75 minutes show as "75:00".
      • computeStreak(winTimes, now, timeZone) in stats/streak.ts counts the days in a row with a win. SQLite has no time zones, so every implementation uses this function. It groups times by calendar day in the player's time zone with one Intl.DateTimeFormat.

      The rule of the streak has one subtle part: today may still get its win. So a streak that ended yesterday is still alive until the end of today. Try it. Click days to mark a win. The orange outline is today, on the right.

      The real function looks back over the whole history for the longest run. This demo shows only the last 14 days, the same window as Streak.recent.

      11. Putting it together

      Follow one game from start to end and watch which engine function runs. The app owns the screens and the storage. The engine only answers questions.

      What to remember
      • A grid is 81 numbers. Units and peers are tables made once.
      • Candidates are bit masks. One bit stands for one digit.
      • The backtracking solver counts solutions. It proves uniqueness.
      • The technique solver explains solutions. It finds named steps. The grade and the hints stand on it.
      • The generator removes clues while the puzzle stays unique, and keeps a puzzle only at the right grade.
      • A hint is a plan of at most 6 steps, shown rung by rung. The answer comes last.
      • Every function is pure. Time and chance come in from the app as plain values.
