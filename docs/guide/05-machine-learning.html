Chapter 5

The digit model

One small neural network reads every cell of a scanned sudoku. This chapter starts with the basics of neural networks, from zero. Then it follows the model from the first labelled photo to the file on the phone.

Before you read You know programming. You do not need to know machine learning. Each new idea starts with a problem, then an everyday comparison, then a drawing. Then the chapter shows the real file and the real function. The scanner that cuts the cells out of the photo is in chapter 4. The big picture of the whole system is in chapter 1.

The map of this chapter

The model is a small file. It takes a long road to get there. The code of this road lives in ml/, a Python project. The app is TypeScript. The two sides never import each other (SUD-07). They share three things: the contract, the fixtures and the model file.

The task: one cell in, two answers out

The problem. The scanner cuts a photo of a sudoku into 81 small square pictures. Each picture is a cell image. The app needs to know what is in each one. It needs a program that looks at a picture and says "this is a 7". Nobody can write the rules for that by hand. A printed 7 and a 7 in pencil look very different. A crooked photo makes it worse.

The idea. We do not write the rules. We show a program many pictures with the right answers. The program finds the rules by itself. This is machine learning. The program we train is a neural network.

Analogy Think of a child that learns to read digits. You do not explain the shape of a 7. You show 1000 cards and say the digit each time. After some time the child knows. Training a model works the same way. The model is the child. The labelled cells are the cards.

The model gives two answers for each cell (ADR-006).

Why two heads? The digit says which number is in the cell. The kind says how the mark was made. The scanner loads a printed digit as a locked given. It loads a handwritten digit as an entry that the player can edit. A notes cell has small pencil marks. It counts as empty. Only some pairs make sense:

DigitValid kindsMeaning
emptynone, notesA blank square, or a square with pencil notes.
1 to 9printed, handwrittenA given, or a digit the player wrote.

The function is_valid_pair in contract.py checks this rule. The app treats an invalid pair as low confidence. The confidence of a cell is the lower of the two top probabilities. The full text is in the model contract.

Why the whole grid must be right

A sudoku has one rule that matters here: one wrong digit breaks the puzzle. The solver finds no solution, or a different one. So the number we care about is not "how many cells are right". It is how many grids are fully right. The glossary calls this grid-exact accuracy.

The maths is simple. If each cell is right with chance p, then 81 cells are all right with chance p to the power 81. Small errors add up fast. Try it.

A model reads each cell right 99.5 % of the time. About how many of 100 scanned grids come out fully right?

0.995 to the power 81 is about 0.67. Every cell is a new chance to fail. This is why the project measures grid-exact accuracy.

Neural networks from zero

Five ideas are enough to read the rest of this chapter: pixels are numbers, a filter finds a pattern, layers stack the filters, training sets the numbers, and softmax turns scores into probabilities. This section teaches them one by one.

Idea 1: a picture is a table of numbers

A computer does not see a "7". It sees a table of numbers. Each number says how bright one pixel is. A black and white picture has one number per pixel. A colour picture has three: red, green and blue. The model of this project reads one number per pixel. The preprocessing turns the colour into grey first (see preprocessing parity). It also flips the scale: ink is near 1, paper is near 0.

Idea 2: a filter slides over the picture

The problem. A cell has 32 by 32 = 1024 pixels. We could connect every pixel to every decision, but that needs a huge number of weights. It also ignores a simple fact: a "7" is a "7" wherever it sits in the cell. A vertical stroke is a vertical stroke at the left or at the right.

The idea. Use a tiny filter, 3 pixels by 3 pixels. Slide it over the whole picture. At each place, multiply the 9 pixels by the 9 filter numbers and add the results. That is one output number. The result is a new picture: a response map. It is bright where the pattern is. This operation is a convolution.

Analogy A filter is a stencil with a pattern, for example "a vertical line". You move the stencil over the page. Where the page matches the stencil, you mark a bright dot. Where it does not match, you mark a dark dot. A network holds many stencils. It learns them by itself.

It lights up under and over the top bar. A network has 16, 32 or 64 such filters in a layer. Nobody sets their numbers by hand. Training does it.

Two helpers: ReLU and pooling

  • ReLU sets every negative number to 0. It is one line: max(0, x). Without it, a stack of filters would collapse into one big filter. With it, each layer can make a real decision: "the pattern is here" or "it is not here".
  • Max pooling shrinks the picture. It keeps the biggest number of each 2 by 2 block. The map gets half as wide and half as high. The network cares less about the exact pixel and more about "there is an edge near here". It also makes the next layers cheaper.
  • Batch normalisation keeps the numbers in a stable range after each convolution. It makes training faster and steadier. You can read it as "tidy the numbers".

Idea 3: layers build up from edges to digits

The output of one layer is a stack of response maps. The next layer slides new filters over this stack. So the second layer finds patterns of patterns: a corner is a vertical edge next to a horizontal one. The third layer finds curves and loops. At the end, the network has one list of 64 numbers for the whole cell. Each number says how much of one learned pattern is in the cell. Two small heads turn this list into answers.

Idea 4: training sets the numbers

The problem. The network has 72,926 numbers, the weights. At the start they are random, so the answers are random. How do we find good values?

The idea. Make a guess, measure the mistake, and nudge every weight a tiny step in the direction that makes the mistake smaller. Repeat many times.

Analogy You stand in fog on a hill. You want to reach the valley. You cannot see it. But you can feel the slope under your feet. You take a small step downhill. You feel again. You repeat. The height of the ground is the loss. The weights are your position. The step size is the learning rate.

Idea 5: train, validation and test, and the danger of memorising

The problem. A model can score 100 % on the cells it trained on and still fail on new ones. It has memorised the cards instead of learning the rule. This is overfitting.

Analogy A student gets the exam questions in advance and learns the answers by heart. The student scores 100 % on that exam and fails the next one. To test the real understanding, you need new questions.

So we split the labelled cells into three piles, before training starts:

The three piles have three different jobs. The training pile changes the weights. The validation pile checks progress and fits the temperature (later in this chapter). The test pile gives the final honest score. We must not tune the model on the test pile. If we did, the test would turn into another training pile, and the score would be too good. The project guards this further with the fixtures, which no training run ever sees (SUD-10).

Two more tools fight memorising. Augmentation bends each training picture a little at random: shift, rotate, blur, change the brightness. The model never sees the same picture twice, so it cannot learn it by heart. Dropout switches off a few numbers at random during training, so no single number can carry the answer alone. Both appear in the code later.

The validation score of a model gets worse for five epochs, while the training loss keeps falling. What happens?

A falling training loss with a rising validation loss is the sign of overfitting. The model fits the cards it has, not the rule behind them.

Softmax, confidence and calibration

The problem. The last layer of the network gives 10 raw scores for the digit, one per class. They are called logits. A logit can be 5.3 or -2. The app needs something it can use: a chance for each class that adds up to 100 %, and a single number that says how sure the model is.

The idea. Softmax raises e to the power of each score, then divides by the sum. Big scores win much more than small ones. Everything is positive, and the total is 1. The biggest probability is the confidence.

Demo: scores to probabilities

Four classes of one cell. Move the sliders to change the scores. Then change the temperature: a high temperature makes the model less sure. The green line is the 80 % ring threshold of the correction screen.

1.00

Look at what the demo shows. Equal scores give equal chances. A gap of 3 points already gives about 90 % to the leader. The temperature divides all the scores before softmax. A large temperature flattens the bars. A small one makes them sharper. Training can leave a model too sure: it says 99 % and is right only 90 % of the time. The fix is cheap.

Why this way: calibration The app uses the confidence to decide which cells to flag. So the confidence must be honest. After training, fit_temperature in train.py searches one number T on the validation cells with the LBFGS optimiser. The best T makes "90 % sure" mean "right 90 % of the time". The export divides the digit logits by T. The score for the honesty is the expected calibration error (ECE). A recent run had ece = 0.0026 (0.26 %): confidence and accuracy differ by a quarter of a point on average.
Deep dive: cross-entropy, label smoothing and the two losses

The cross-entropy loss looks at the probability that the model gave to the right class. If that is 1.0, the loss is 0. If it is 0.01, the loss is large (about 4.6). So the loss pushes the model to put all its chance on the right answer.

Label smoothing (label_smoothing = 0.05) says the right answer is "95 % this class, 5 % spread over the others". Why? Some labels are wrong, because people make mistakes. If the model must reach 100 %, a wrong label pulls hard. A small smoothing keeps the logits from growing without limit and makes the model less proud.

The function loss in train.py adds two terms:

total = cross_entropy(digit_logits, digit, label_smoothing) total += kind_weight * cross_entropy(kind_logits[known], kind[known]) # kind_weight = 0.4

A cell whose kind nobody knows has the target UNKNOWN_KIND = -1. It adds no kind loss, so the missing label does not harm the digit. The weight 0.4 stops the kind head from pulling the shared features away from the digit (ADR-006).

A model gives a cell the probabilities 0.55 for "3" and 0.45 for "8". What should the app do with this cell?

The confidence is the top probability, 0.55. It is below REVIEW_CONFIDENCE (0.8), so the correction screen draws a dashed ring around the cell and the player checks it.

The real network: CellClassifier

Now you know every part. The class CellClassifier in ml/src/sudoku_ml/model.py is built from them. It follows ADR-006: three stages of two convolutions, then global average pooling, then two linear heads. Click a box to learn what it does.

Click a box to read about it.

Input: 1 x 32 x 32

The scanner gives a 64 x 64 colour cell. The preprocessing turns it into 32 x 32 numbers between 0 and 1. Ink is near 1, paper is near 0. The model reads the whole cell, including the grid lines at the edge (ADR-020). The function is preprocess_cell in preprocess.py.

Stage 1: 16 filters, two times

Two convolutions with 16 filters each find the simplest patterns: strokes, edges, dots. Then a 2 x 2 max pool halves the size to 16 x 16. This stage has 2,512 weights. _conv(1, 16) and _conv(16, 16) in model.py build it: a 3 x 3 Conv2d with padding=1 and no bias, then BatchNorm2d, then ReLU.

Stage 2: 32 filters, two times

More filters, smaller picture. The filters here see bigger parts of the cell, because the picture is already smaller: corners, bends and short curves. A max pool gives 8 x 8. 13,952 weights.

Stage 3: 64 filters, two times

The biggest stage: 55,552 weights, three quarters of the model. The filters now describe parts of digits: a loop at the top, a stem, a diagonal. There is no pooling here, so the picture stays 8 x 8.

Global average pooling and dropout

Each of the 64 maps (8 x 8) is replaced by its average. The result is one list of 64 numbers: how much of each learned pattern is in the cell, wherever it sits. This makes the model less sensitive to a small shift. The first design used a big dense layer here and scored lower (97.5 % against 98.7 %, see the research record). Dropout 0.1 switches off 1 of 10 numbers at random during training.

Digit head: 10 classes

nn.Linear(64, 10). It multiplies the 64 numbers by a table of weights and gives 10 logits: empty, 1 ... 9. Softmax (in ExportModel) turns them into probabilities. The fitted temperature divides the logits first.

Kind head: 4 classes

nn.Linear(64, 4). It reads the same 64 numbers as the digit head. That is the point of ADR-006: what a "7" looks like is learned once, and both answers use it. One model, one file, one pass on the phone. The kind head has no temperature: its softmax is plain.

A conv layer has in x out x 3 x 3 weights. Example: 32 to 64 gives 32 x 64 x 9 = 18,432. Batch norm adds 2 numbers per channel. A linear layer has in x out + out. The sum matches the number in the ADR and in metrics of the first run. 72,926 float32 numbers are 292 KB. The rest of the 326 KB file is the structure of the model.

ExportModel wraps the network for the phone. It permutes the input from NHWC (the app's layout: batch, height, width, channel) to the NCHW layout that PyTorch uses. It divides the digit logits by the temperature and applies softmax to both heads. So the phone gets probabilities, not logits.

The data

The problem. The model learns what the data shows. If the data has only clean printed digits, the model fails on a crumpled newspaper in poor light. The data needs to be big, varied and correct. A model is only as good as its labels.

Two kinds of data train this model:

What: cells that a program draws. render_cell in synthetic.py draws a digit with a random font from ml/fonts/ (seven open-licence families), at a random size and offset. Then it makes the picture imperfect, as a camera would:

  • a random paper colour and a random ink colour (15 % coloured ink)
  • a small rotation and a shift of the digit
  • sometimes part of a neighbouring digit at the edge (20 %)
  • leftover grid lines at the border (up to 4 sides)
  • blur and random pixel noise
  • for notes cells: 2 to 5 tiny digits in a 3 x 3 pattern

Why: it is free, it needs no labelling, it is perfectly correct, and the generator and its seed are the dataset. Nothing is stored (ADR-009). Limit: synthetic cells have no handwriting, so they cannot teach the model the kind handwritten. They give printed, notes and empty only.

What: cells cut from real photos of sudokus: phone photos of newspapers and books, web images, public datasets, and the scans that players upload from the app (when the setting "Help improve the app" is on, SUD-02). The scanner cuts each photo into 81 cells.

Why: only real cells show real paper, real light and real handwriting. Cost: a person must label each cell. That is the job of the labelling app.

Training mixes both: each batch takes half synthetic and half real cells (see train_model). The synthetic half teaches the clean shapes. The real half teaches the mess.

Every image in the store comes from a source in ml/DATA_SOURCES.md. The rule: do not use a source that is not in the table. The table says where the images come from, the licence, and whether a model or image may be published.

Where the data lives: one folder, two tables

Images are big and may not be public, so they stay out of git (ADR-009). But a model is only reproducible if you know exactly which images trained it. The answer of ADR-018 is a small table in git next to a big image store outside git.

The digit of a cell is its folder. The folder is the truth, and the digit column must match it (just check-data tests this). The kind is a column. Two more columns link a cell to its sudoku photo: photo_id, row and col. This link matters for the split.

The journal is the trick that makes labelling safe. Every click is one line in work/journal.jsonl, saved at once. Finish folds the journal into cells.csv. So the diff of a labelling session is a few changed table rows, not thousands of log lines (ADR-018). The code is write_cells_manifest in manifest.py and finish in finish.py.

Rule SUD-08 Do not commit training images or private fixtures. Cells, photos and model files stay on the Mac. Notebooks use synthetic images by default for the same reason. The guide shows drawings of cells, never real ones.

Labelling: how a photo becomes trusted cells

The problem. A model can only be as correct as its labels. A wrong label teaches a wrong rule. And there are many cells: the dataset has tens of thousands. A person cannot type each digit from zero.

The idea. Let the current model guess first. The person then only checks the guesses, most doubtful first. This is faster than typing, and the person still has the last word. The tool is the labelling app: a React app in tools/label-app/ and a Python server ml/src/sudoku_ml/label_server.py that holds all the rules (ADR-034). It runs on 127.0.0.1 only. A photo never leaves the Mac while you label (SUD-02). Start it with just label-cells.

1. Fetch new scans

Players can upload the scans they corrected on the phone (setting "Help improve the app"). The step downloads them from the cloud of the chosen stage (just pull-scans does the same without the app). It also takes photos from just import-photos <folder> and loose cells in unlabeled/. After the fetch, the model guesses every open cell.

2. Outlines

The scan cut the photo along four corners. If a corner is wrong, all 81 cell labels of that scan are wrong. So a person looks at the outline of each scan first, the most doubtful first. Click a bad outline. Enter approves the rest. A bad one opens large: drag the corners, or press R to reject the photo. No cell of a scan trains the model before its outline is approved.

3. Digits

The open cells appear as galleries, one tab per digit (Empty, 1 to 9, No guess). The cell with the most doubt comes first. Point at a cell: the side panel shows the whole sudoku with the cell marked, the model's probabilities and the reasons for the doubt. Type a digit to fix. Press X to discard a bad cut. Enter confirms the page. "Confirm the sure ones" confirms every cell of the tab that the model reads at 98 % or more.

4. Kind

For the cells of 1 to 9 the person marks the kind: P (printed), H (handwritten) or U (unsure). Training ignores unsure. The sure-threshold here is 95 %. Finish refuses while cells still wait in this step.

5. Finish

finish in finish.py folds the journal into cells.csv, runs the data check, writes STATUS.md, and deletes the journal. Each cell that a person confirmed gets the label source verified. Then the developer commits the tables: git add ml/dataset. Git never adds the images.

How the order of doubt works

The tile of a cell has an edge from red (doubtful) to green (sure). doubt.py adds up small signals. Each signal keeps its evidence, so the app can say why. The signals only set the order. A person still checks every cell.

SignalIdea
low probabilityThe model gives its own label less than 90 %.
model reads another digit or kindThe top guess is not the label.
the player changed itThe player edited this cell on the phone (app-edited). Players fix real mistakes, so this is evidence.
a rule is brokenThe same digit twice in a row, column or box. This needs no model.
not uniqueThe printed givens have more than one solution. A real puzzle has one. sudoku_signals.py counts solutions with its own small solver, because SUD-07 forbids importing the TypeScript one.

Which labels train the model

Every cell has a label_source. The training code reads only the trusted ones: TRUSTED_LABEL_SOURCES = ("", "verified") in tables.py. The empty value is for old cells from before this field existed. app-edited and app-unedited labels come from a phone scan that nobody has checked yet. They stay out of training until a person confirms them. The function training_cells in dataset.py applies the rule.

Why this way? A model that trains on its own unchecked guesses learns its own mistakes. The loop would feed itself. The person in the loop is the guard against that. The cheap tools (order by doubt, confirm the sure ones) make the person fast, not optional.

Kind checks: how good are the labels?

How do you measure the quality of labels that a person made? You ask the person again. The blind check (kind_check.py) shows old cells again, after at least 7 days (MIN_AGE), so that the developer no longer remembers the first answer. The share of equal answers is the agreement. It estimates the label noise. The answers go in kind-checks.jsonl and never change a label. Training copies the last agreement into the model card, so you can see how far the kind labels can be trusted. The tool just suspects does the other direction: it trains models on parts of the data and lists the cells whose label a model doubts most (suspects.py).

A phone scan arrives with a wrong outline, one corner is off. Why does the labelling flow check the outline before the cells?

The cells are cut along the outline. A wrong outline moves the cut, so the cell images do not match the grid positions. Training uses a scan's cells only after a person approved its outline.

The split: by sudoku page, not by cell

The problem. Remember the three piles. The test pile must hold cells the model has never seen anything like. The easy way to split is to shuffle all cells and deal 80 / 10 / 10. That looks right. It is wrong, and the project learned this the hard way.

The 81 cells of one photo share the same font, the same paper, the same light and the same camera. Two photos of the same newspaper page are nearly the same picture. If one cell of a page sits in training and its neighbour sits in test, the test is not a new question. The model has seen the "sibling". It scores better than it would on a new photo.

Analogy A teacher gives an exam. The questions are new, but the students already did the same exercise with other numbers. They pass. The result says nothing about how they handle a really new exercise. To test for real, the whole exercise sheet must be kept out of the lessons. Here, the sheet is the sudoku page.

ADR-035 measured the leak on the real data: 3,189 of 5,735 test cells (55.6 %) had a photo that also had training cells. Six of seven pairs of photos of the same page sat on different sides. The test accuracy was too high.

How the code builds the split

All the code is in ml/src/sudoku_ml/dataset.py. The entry point is split_cells. Training, the suspect ranking and the labelling app all call the same function, so they agree on which cells are test cells.

1. Find which photos show the same page

page_keys compares the labelled digits of every two photos. Two photos show the same page when they share at least 10 digit cells at the same row and column (SAME_PAGE_MIN_DIGITS), and 90 % of these hold the same digit (SAME_PAGE_AGREEMENT). It uses a matrix product on one-hot tables, so it takes milliseconds for hundreds of photos. The key of a page is its smallest photo id. A cell of any photo gets the key of its page.

2. Join the cells that belong together

group_ids joins groups with union-find. Two rules: cells whose 64-bit difference hash (dhash) differs by 4 bits or fewer join, and all cells with the same page key join. A cell with no photo link keeps only the first rule. The difference hash is a tiny fingerprint: shrink the cell to 9 x 8, and for each pixel record "is it brighter than its left neighbour?".

3. Choose the key of each group

split_by_group gives each group one key: the smallest key of its members. The key of a cell is its page, or else its file name. A group is never cut in two, so the cells of a page can never land on two sides.

4. Hash the key to a pile

side_of takes the SHA-256 of the text "<seed>:<key>", reads the first 8 bytes as a number between 0 and 1, and compares it with the split fractions. The side depends only on the key and the seed. A new cell never moves an old group.

Deep dive: why hash the key, and why not shuffle

The first version of the split shuffled the list of all groups with the seed. One new cell changed the list. That moved old groups to other piles. So after each fetch of new scans, the "test set" held other cells, and the scores of two runs could not be compared.

A hash has no list. The pile of a group depends only on its own key and the seed. New data adds groups, and it leaves every old group where it was. The price: the sizes of the piles vary more. A photo holds up to 81 cells, so one photo more or less in the test pile moves its size. On the tables of 2026-10-23, the test pile has 1,884 cells (5.5 %) and the validation pile 2,100 (6.1 %), where the plan said 10 % each. The score then has a wider confidence interval. The ADR names a trigger: if the test pile falls under 1,000 cells, raise its fraction or keep a fixed holdout of whole pages.

Why must the 81 cells of one photo end up on the same side of the split?

A leak makes the test easier than the real world. The real world gives the model a photo it has never seen, with all its cells new.

Training: one command, one run folder

You know the loop. Here is how the project runs it. One command trains the model:

Two pools, half and half

The class Pool holds the images, the digit targets, the kind targets and per_batch. With batch_size = 256, each pool gives 128 cells per batch, drawn with replacement (torch.randint). The synthetic pool is large and clean. The real pool is smaller and messy. This mix keeps the real mess in every step. Without real cells (real_cells = false), the synthetic pool fills the whole batch.

Augmentation

augment in augment.py bends each 64 x 64 cell at random before preprocessing: shift up to 4 px, rotate up to 6 degrees, scale 10 %, shear, blur (in 40 % of cells), gamma, contrast, brightness and noise. It is one affine_grid and grid_sample call on the whole batch, so it is fast, also on the GPU. The model never sees the same cell twice.

Preprocessing

preprocess_batch in preprocess.py: grey, invert, shrink to 32 x 32 with an exact area average. It is the same maths as the phone does, written for a batch of tensors. See preprocessing parity.

The model

Returns digit logits (256 x 10) and kind logits (256 x 4). In training mode, batch norm uses the batch numbers and dropout is on. predict_logits puts the model into eval() mode for scoring.

Loss and optimiser

The loss is the digit cross-entropy (with label smoothing 0.05) plus 0.4 times the kind cross-entropy. AdamW turns the slope into a nudge. The OneCycleLR schedule raises the learning rate to max_lr = 0.003 in the first part of the run and lowers it again toward the end. Big steps early find the valley. Small steps late settle in it. An epoch has (cells in all pools) // batch_size steps.

A run writes one folder in ml/artifacts/, named with the time and the config name. The folder is not in git. It holds everything you need to judge, export and reproduce the run:

The model card records a hash of cells.csv. The tables are in git, so this hash names the exact dataset version that trained the model. This is why ADR-009 keeps the images out of git but the tables in.

Deep dive: the five calls of train()
train(config) load_data real cells (read_real_cells + split_cells), synthetic cells (seed and seed+1) train_model two Pools, then fit(...): the loop above evaluate fit_temperature on val, then every score on test write_run model.pt, metrics.json, model-card.md

load_data draws the synthetic training cells with seed and a second small set for kind scores with seed + 1. The fixtures use 2026. If a config sets a seed so that seed or seed + 1 equals 2026, the run stops. Why? Fixture cells and training cells must never be the same pictures (SUD-10). The device is mps (Apple GPU) when present, else the CPU (default_device). A real run takes minutes on a MacBook.

Fixtures: the exam that training never sees

The test pile is cut from the same data as the training pile. Even split by page, it is "more of the same". For the final check, the project keeps fixtures: whole scans, with the truth for all 81 cells, that no training run may ever use (SUD-10). They are in shared/fixtures/scans/: <split>/<id>/photo.jpg, truth.json and cells/00.png ... 80.png. The split is dev (used to choose between runs) or holdout (looked at only at release time, so that choosing the best run does not overfit the gate).

The classifier is scored on the cell images that the app's own scanner produced from each photo, so there is no second scanner in Python (ADR-007). The score is grid-exact: the share of fixtures where all 81 digits are right. Public fixtures are puzzles this project made, so they may be published. Private fixtures (real newspapers and books) stay on the Mac (ADR-013).

State of the code The folder shared/fixtures/scans/ holds only its README today. The preprocessing fixtures (shared/fixtures/preprocess/) exist and are in use. The grid-exact scoring is part of the planned promote gate (M3). Until then, the test pile and the on-device measurements in measure-quality are the evidence.

Export: from PyTorch to a phone file

The problem. The model lives in PyTorch, in Python. The phone cannot run PyTorch. It runs TFLite (also called LiteRT), a small runtime that Google builds for phones. We must translate the model, and we must be sure the translation gives the same answers.

Analogy You write a book in English. The reader speaks another language. You hire a translator. Then you do not trust the translator blindly. You ask a second person to translate a few pages back, and you compare them with the original. If a sentence changed meaning, you stop.

just export artifacts/<run> does this (ml/src/sudoku_ml/export.py, ADR-005). It does the work and then checks the result five ways. A failed check raises an error and no file is promised.

1. Wrap the model for the phone

ExportModel adds what the phone needs. The input has the layout NHWC (batch, height, width, channel), which is what the app sends. It is permuted to the layout PyTorch uses. The digit logits are divided by the fitted temperature. Softmax makes both outputs probabilities. The result is a dictionary with the names digit and kind.

2. Convert

One call: litert_torch.convert(wrapped, (sample,)).export(path). Google's tool traces the PyTorch model on the sample and writes a .tflite file. The sample is the 81 reference cells (a batch of 81, static). All weights stay float32: no float16 and no int8 in v1. A model this small (under 1 MB) does not need the saving, and a smaller number format would add risk.

3. Check the file itself

check_op_versions reads every operation in the file and compares its version with tflite_2_17_ops.json. The phone bundles TFLite 2.17 (through react-native-fast-tflite). A newer op version would crash on the phone, not on the Mac. check_float32 finds constants that are not float32 (int shape constants are fine). The size must stay under MAX_BYTES = 1,000,000.

4. Run both and compare

The export runs the new file with the Python TFLite interpreter and runs the PyTorch model on the same 81 cells. The largest difference must be under 1e-3. The top class of both heads must agree on every cell (check_same_argmax). One real run showed a difference of 1.19e-7: the same numbers, within float rounding.

5. Write the evidence

export.json records the contract version, the input shape, the index of each output, the largest difference, the size and the ops. reference-outputs.json holds the 81 inputs (base64) and the PyTorch probabilities. The app later runs the model on the phone and compares with this file, so a broken phone runtime shows up in a test.

Why outputs are found by index The phone runtime returns outputs in tensor order and its names are not reliable. So export finds the head by its width (10 is the digit, 4 is the kind) and records the index in manifest.json: "outputs": {"digit": 0, "kind": 1}. The scanner reads the map and checks the shapes [81, 10] and [81, 4] before it trusts a number.

Preprocessing parity: two kitchens, one recipe

The problem. The model was trained on numbers made by a Python function. On the phone, the numbers come from TypeScript. If the two functions differ a little, for example the order of grey weights, or ink = 1 against ink = 0, nothing crashes. The model quietly gives worse answers on every scan. This kind of bug is very hard to find.

Analogy Two kitchens cook the same dish from one recipe. If one cook uses a teaspoon where the recipe says a tablespoon, the dish tastes wrong, but nobody gets an error. The fix is a taste test: both kitchens cook the same 81 samples and you compare them.

The "exact area average" in step 3 sounds hard. It is not. 64 to 32 is a factor of two. Each output pixel is the mean of a 2 x 2 block. The function area_weights builds the weight matrix W (32 x 64) so that the same code also works for other sizes (to_cell_image uses it for real cells of 71 x 71). No OpenCV is needed on either side, so the result does not depend on a library build.

The taste test is a folder of 81 pairs:

shared/fixtures/preprocess/ 00.cell.png a synthetic 64 x 64 cell (drawn, never a real photo) 00.expected.json {"shape": [32, 32], "values": [[...]]} the answer, 6 decimals ... 80.cell.png 80.expected.json

Python and TypeScript both read these pairs. Every value must match within 1/255. The pairs are made with just preprocess-fixtures, which overwrites the committed files. The same 81 cells are also the batch for the export, so one set of files pins both the preprocessing and the model.

Rule SUD-09 and the contract version The contract has a version (CONTRACT_VERSION = "2.0"). A change of the input size, the crop, the polarity or the class list is a major change. The scanner declares the majors it implements. The install step and a unit test refuse a model of another major. Contract 1 cropped the cell to rows 6..57. Contract 2 reads all of it (ADR-020). A contract-1 model would read a full cell wrongly.
Deep dive: why not just resize with a library?

Libraries differ. A bilinear resize in one library is not the same as in another. They differ at the sub-pixel level, and many use anti-aliasing in different ways. A model is sensitive to such small differences, because its filters read the exact edge shape. By defining the resize as a matrix product, the contract fixes the numbers and each side can implement it in a few lines. The contract text notes that OpenCV INTER_AREA on float32 agrees within 4e-5 grey levels, so you can use it as a second check, but no side needs it.

The TypeScript preprocessing forgets to invert the grey (ink = 0 instead of ink = 1). What happens first?

That is the job of the 81 reference pairs. Without them, the bug would stay hidden: the app would run and give wrong digits.

The promote gate: who may enter the app?

The problem. Training makes many runs. Most are experiments. The app must ship exactly one model, and a person must be able to say why this one. The rule is SUD-06: a model reaches mobile/assets/models/ only through just promote-model. This keeps a bad run from reaching players by accident.

What exists today just promote-model is planned for milestone M3. It is not in the justfile yet. Today the one exception of SUD-06 is just install-model. It copies an exported run without the scoring checks (ADR-007, amendment 2026-10-11). The stepper shows the full gate. The table after it shows what the install step does now.

1. Check the contract

The run must say which contract it implements (export.json). If the major version is one the scanner does not know, the gate refuses (SUD-09). This one check already exists in install.py.

2. Score the dev fixtures

The gate runs the model on the 81 cell images of each dev fixture. The cell images are the ones that the app's own scanner wrote. The score is grid-exact: the share of fixtures with all 81 digits right (and the kinds right).

3. The absolute floor

The score must reach the quality targets QR-01, QR-02 and QR-03 of chapter 10: at least 95 % of newspaper scans, 85 % of curved book pages, and a single cell at 99.94 %. This applies once the fixture set is big enough to mean something.

4. Not worse than the current model

The new model may not be worse than the model in the app by more than one fixture grid, on the grid-exact score of either split. For the very first model only the floor counts. This stops a regression that looks fine on the average.

5. Score the holdout, but only record it

The holdout split is not looked at while you choose between runs. The gate scores it and writes the number in the manifest. A human reads it only when deciding a release. This keeps the "pick the best on dev" habit from overfitting the gate itself.

6. Copy and commit

The model is copied as cell-classifier.tflite (a stable name, because React Native needs a fixed require()). manifest.json is rewritten with the version, contract, output map, metrics, holdout and date. The promotion is its own commit, for example feat(model): cell-classifier 1.2.0, dev grid-exact 96 % to 97 %.

On the phone

All inference runs on the device (ADR-003). The game works offline. The live outline needs zero delay. A running server would cost money for each scan and would send the photo away. The model is under 400 KB, so nothing here needs a server.

  • react-native-fast-tflite runs the model with TFLite 2.17 on the CPU. It does not use the Metal GPU delegate.
  • mobile/src/scanner/classifier.ts reads manifest.json, loads the model, and checks the contract and the output shapes. On a mismatch it turns scanning off with a message instead of giving wrong digits.
  • The scanner sends all 81 cells in one batch: the input is [81, 32, 32, 1]. The model has a static batch size of 81.
  • The answer is two tables, [81, 10] and [81, 4]. The confidence of a cell is the lower of the two top probabilities. A low value gets a dashed ring on the correction screen.

How the scanner finds the grid, cuts the 81 cells and uses these answers is the story of chapter 4. How the correction screen uses the confidence is in chapter 3.

The private model: why the .tflite is not in git

A model that trained on real_cells = true learned from images with unclear licences (newspapers, web photos). So it may not be published (ADR-013). Training does not filter by licence yet, so every real run is private. The rule in practice:

  • mobile/assets/models/*.tflite is in .gitignore.
  • manifest.json and reference-outputs.json are in git. git log mobile/assets/models shows the history of the manifest, not of the bytes. The run field in the manifest points to the run folder in ml/artifacts/.
  • A new clone or a new worktree has no model file. The app does not bundle without it. Run just install-model artifacts/<run> first. The iOS recipes ios-measure and ios-simulator stop with "The model is missing. Run: just install-model <run>".
  • CI bundles the app with an empty placeholder file.
Pitfall Do not delete ml/artifacts/ or the image store when you tidy. The model and the data are not in git. Until there is a backup, they exist once.
