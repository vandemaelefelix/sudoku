Chapter 6

Backend, accounts and sync

The app works alone. Yet it also has a small cloud part. In this chapter you learn why it exists, which pieces it has, how a player signs in, how finished games travel between two phones, and how a scan reaches the training set. You also learn what to do when a piece breaks.

How to read this chapter Read it top to bottom once. Then come back for the parts you need. The two big hands-on parts are the deployment map and the two-phones simulation. If you have not read the big picture yet, start with chapter 1. The local storage that the sync wraps is in chapter 3.

1. Why a backend, if the app is offline-first?

Start with the rule. SUD-01 says the game and the scanner must work fully without a network. A player on a plane plays sudoku. A player who never makes an account never sees a server. So the phone stays the source of truth.

Rule SUD-01 Play and the stats MUST NOT wait for the network or an account. Every backend feature in this chapter is optional, and every one of them fails quietly.

So why build a backend at all? Two reasons come from real players.

  • A backup. A player loses the phone. Without a copy, ten years of finished games are gone.
  • Two devices. A player has an iPhone and an iPad. They want the same history and the same stats on both.

A third reason comes from the developer. The cell classifier learns from real photos. The app can send a finished scan, with the corrections of the player, so the developer labels less by hand. That is the scan collection (section 12).

Analogy Think of a paper notebook and a photocopy shop. You write in the notebook every day. It always works. Now and then you drop by the shop and leave a copy of the new pages. If the shop is closed, you lose nothing. You try again next week. If you lose the notebook, the shop gives you the copies back. The notebook is the phone. The shop is the cloud.

Why does each phone count the stats itself?

DynamoDB cannot count or group rows like SQL does. The stats screen would need a network too. Instead every phone downloads the full history once and runs the same SQL as always (ADR-023). This costs a few megabytes in ten years of daily play. In return the stats screen works offline and one set of rules counts everything. The leaderboard is different: it compares players, so the cloud will count it later.

2. The platform in plain words

The developer knew TypeScript and a little AWS. The developer did not want to run a server. So the platform is serverless: you give AWS code and rules, and AWS runs them when a request arrives. You pay only for what runs. For a hobby project that is close to zero. ADR-027 holds the decision. Here are the pieces.

AWS Lambda

A Lambda is one function. AWS starts it when a request comes in, and stops it when it is done. Our sync function is backend/api/src/handler.ts.

API Gateway

The API Gateway is the front door. It owns the public URL. It checks the token and the speed limit before our code runs.

DynamoDB

A key-value database that AWS runs for us. We use one table, on demand, so an idle table costs nothing. No SQL, no connections.

S3

A bucket for files. We use one private bucket for the scan photos. A Lambda never handles the photo bytes. The phone uploads straight to S3.

SST

SST describes all of this in TypeScript. sst.config.ts at the repository root imports one file per area from backend/infra/.

Clerk

Clerk is a third party that signs players in. It sends the emails, holds the Google sign-in and gives the app a signed token. We never store a password.

Why these choices (ADR-027)? Clerk gives native Google buttons and free use up to 50,000 monthly users. DynamoDB gives 25 GB free forever and one partition per player fits the history. The API Gateway JWT authorizer means no code of ours checks a token, and a bad token never reaches the Lambda. SST means the developer writes TypeScript, not Terraform.

Three stages

A stage is one full copy of the backend. There are exactly three. SST refuses any other name, so a typo cannot create a fourth copy by accident (STAGES in backend/infra/config.ts).

StageDeployed byClerk instanceRemoval

Only production creates the account-wide things: the budget, the alarm topic of the kill switch and the GitHub trust. AWS allows one of each, and one budget per stage would send three emails per alert.

A guard against the wrong account The developer also has employer AWS profiles. A deploy to the wrong account would be a real mistake. So three layers stop it: the just recipes, app() in sst.config.ts (it refuses access keys and any other profile) and run() (it compares the account ID before any resource exists). This guide does not print the account ID. It is a committed constant in backend/infra/config.ts.

The iPhone app

It keeps everything in SQLite and works alone. Two folders talk to the cloud: mobile/src/account/ (Clerk, tokens, delete account) and mobile/src/sync/ (the sync service). A third, mobile/src/scanShare/, uploads scans. The game and the stats never import these folders. A dependency rule enforces that.

The app variants matter: the development variant talks to stage felix, the production variant to production.

Clerk

Clerk signs the player in (email with a code, or Google). It has two instances: a development instance for felix and dev, and a production instance on a custom domain. The app asks Clerk for a short token (60 seconds) before every request. The token comes from the JWT template sudoku-api, which adds "aud": "sudoku-api". The Lambda also calls Clerk once: to delete the user when the player deletes the account.

SST

SST is the tool, not a running box. sst.config.ts decides the stage rules: three names only, production is protected and retained, every resource gets the tags project and stage. It also runs the account guard and refuses a stopped stage. Its state lives in S3 buckets inside the same AWS account.

The Vercel site

A static page with a home page and the privacy policy. web/build.mjs renders docs/privacy/privacy-policy.md to HTML. The site has no JavaScript, no cookies and no analytics. The DNS of the domain also sits at Vercel, and it holds the records that Clerk needs. More in section 13.

API Gateway (the front door)

One HTTP API per stage, built in backend/infra/api.ts. It has three routes. Two use the JWT authorizer: it checks signature, issuer, audience and expiry. A bad token gets 401 and our code never runs. POST /v1/scans has no authorizer, because a player who is signed out can share a scan too.

Each route has a speed limit: 1 request per second with a burst of 10. The scans route is tighter: 0.5 per second, burst 5. CORS is off, because only the native app calls it. The access log has no IP address and no user agent.

The sync-api Lambda

One function for POST /v1/sync and DELETE /v1/account. Node 24, arm64, 512 MB. The general default is a 10 second timeout, but this function sets 30 seconds, because the account delete removes rows in pages. It is linked to the table and to the Clerk secret key. The kill switch can set its concurrency to 0.

The scans Lambda

A separate function for POST /v1/scans (ADR-030). It is separate on purpose: abuse of the public route must not starve the sync. It checks a shared app key, validates the scan record, optionally verifies the token, writes one row and returns a presigned S3 URL.

The DynamoDB table

One table, SyncTable, on demand. It holds identity rows, game rows, daily count rows and scan rows. Section 11 draws it. Its layout lives in backend/api/src/tableDesign.ts, and both the deploy and the tests read that one file, so the test table always matches the real one. Point-in-time recovery and deletion protection exist only in production.

The S3 bucket

Private and encrypted. It keeps scan photos for 365 days, then a lifecycle rule removes them. The app uploads to it directly with a presigned URL that signs the exact file length. The Lambda never sees the bytes.

The budget

One AWS Budget for the whole account: $10 a month. It emails at $3 forecast and at $6 actual. A third alert at $9 actual publishes to an SNS topic and starts the kill switch. Credits and refunds do not count, so a credit cannot hide a cost spike. This is the money rule SUD-11.

The kill switch

One Lambda for the whole account (code in backend/kill-switch/). It finds every stage, sets the SSM flag first, sets the route throttle to 0 and sets the concurrency of sync-api to 0. It emails a summary. A failing step does not stop the others, and every call is safe to repeat, so SNS may retry the run.

The SSM flag

A free parameter /sudoku/kill-switch/<stage>. SST does not own it, so a deploy never removes it. While it exists, four layers refuse a deploy of that stage (the just recipe, the CI workflows and run()). A deploy would otherwise set the throttle again. Only just api-on <stage> clears it.

GitHub Actions

CI deploys dev on each merge to develop, and production on a manual start. It takes an AWS role through OIDC: GitHub proves who it is with a short-lived token, so no AWS access key exists anywhere. The trust policy names one repository and one workflow file. Before any sst command, the workflow checks the account and the kill-switch flag.

A request arrives with an expired token. Where does it stop?

The JWT authorizer checks signature, issuer, audience and expiry. It answers 401 itself. The Lambda only reads the sub from claims that API Gateway already verified.

4. Keeping the bill small: SUD-11 and the kill switch

A public API can be abused. A bug can also loop. The developer set one hard limit: the AWS bill must stay below €10 a month. The rule is SUD-11. The design does not trust one defence. It stacks several, from fast and cheap to slow and final.

If the condition fails, nothing is stored for that entry. Section 10 shows the code. The count never gives a 429. At the cap the server stores what fits and still runs the pull. The other entries stay on the waiting list of the phone for tomorrow.

What exactly does the kill switch do, step by step?
  1. The budget alert at $9 publishes a message to the SNS topic KillSwitchTopic.
  2. SNS calls the kill-switch Lambda. Any message on the topic stops every stage.
  3. For each stage, it writes the SSM flag first. If a later step fails, a deploy is still blocked.
  4. It finds the HTTP API by its tags project and stage. It sets rate and burst of every route to 0.
  5. It finds the sync function by the name prefix and sets its reserved concurrency to 0.
  6. It emails a readable summary. The raw budget email still arrives if this Lambda crashes.

A reserved concurrency above 0 is not possible on this account (AWS needs 100 unreserved executions left). Zero is allowed. So the throttle is the real stop, and the concurrency stop is best effort. The code is in backend/kill-switch/src/killSwitch.ts. To turn a stage on again, the developer runs just api-on <stage>. It shows the month's cost, asks for y, restores the throttle, removes the concurrency stop and clears the flag last.

Open question in the docs AWS does not say whether it bills a request that the throttle turns away. Until a test shows the answer, the docs treat a throttled request as billed. It costs at most $1 per million. If the test shows a bill, the kill switch will delete the stage instead of throttling it.

5. Accounts: who is this player?

The server must know whose games it stores. But we do not want to run a password database. So we use Clerk for sign-in, and we keep our own small mapping on the server.

Analogy: a festival wristband Clerk is the ticket office. After you show your ID, it gives you a wristband. The wristband is only good for 60 seconds, so a stolen one is nearly useless. The API Gateway is the gate guard. The guard checks the wristband and lets you in. Inside, the Lambda does not use your name. It uses an internal member number that only we know. That number is our user ID.

Sign-in on the phone

The sign-in screens are in mobile/src/account/. A player can sign up with an email and a 6-digit code (useEmailSignUp, useEmailSignIn) or with Google (useGoogleSignIn). Apple comes later, when the developer joins the Apple Developer Program. Clerk does the real work. The code in the app calls the @clerk/expo SDK through a small wrapper called the Clerk adapter (clerkAdapter.utils.ts). In tests, a fake adapter replaces it.

The account is optional. The account section in Settings is the only door. A player who never opens it never sees a Clerk screen, and nothing uploads.

One fresh token for each request

Before each sync request, the app calls getApiToken(). The adapter asks Clerk for a token from the JWT template sudoku-api. Clerk keeps the token while it is valid and renews it. After a 401, the app asks again with skipCache: true, so it gets a brand new token. Step through the journey of one request.

1. The app asks for a wristband

The app calls getToken({ template: 'sudoku-api' }). Clerk returns a signed token, a JWT. It lives 60 seconds. It holds the issuer (iss), the audience (aud = sudoku-api), the expiry and the player's Clerk user ID (sub).

2. The app sends it

The request carries the header Authorization: Bearer <token>. The body holds the games. The app never puts the user ID in the path or the body.

3. The guard checks the wristband

API Gateway downloads the public keys of Clerk once and caches them. It checks the signature, the issuer (an exact match with CLERK_ISSUER in backend/infra/config.ts), the audience and the expiry. A fake or old token gets 401. The Lambda never runs and nothing costs a Lambda run.

4. The Lambda reads the claims

subOf(event) in http.ts takes sub from the claims that the gateway already verified. This is the rule of ADR-027: the player comes only from the token. An attacker cannot ask for another player's rows by changing the body.

5. The Lambda finds the member number

findOrCreateUserId reads the identity row IDENTITY#clerk#<sub> with a consistent read. A new player has none, so the Lambda writes one with a random UUID. The write has the condition attribute_not_exists(pk), so two parallel first requests cannot make two member numbers.

6. Everything else uses the member number

Every other row of the player has the partition key USER#<userId>. No email and no name is stored on our side. If the identity row is a tombstone, the Lambda answers 410 and creates nothing.

Why map the Clerk ID to our own ID? If the key of every row were the Clerk ID, a switch of sign-in provider would rewrite every row. With an identity row per login, a new provider only adds an identity row that points to the same user ID. The cost is one extra read per request. ADR-027 judged it worth it.

On the phone: the owner

The phone never sees our user ID. On the phone, every history entry has an owner: the Clerk user ID. The column is owner_id in game_history (migration 5). A game finished while signed out has no owner (null). Every query for the stats or the sync filters on the owner. That keeps two accounts on one phone apart.

There is one more detail. At app start, Clerk needs a moment to load. The app must not wait for it (SUD-01). So the app keeps the last signed-in Clerk user ID in the iOS Keychain (the owner cache, ownerCache.utils.ts). At start the owner is this cached ID. A game that the player finishes offline gets the right owner even before Clerk has answered.

6. Deleting an account (and the 410)

Apple requires that an app with accounts lets the player delete the account inside the app (guideline 5.1.1(v)). Deleting means three things in three places: our rows, the Clerk user, and the data on the phone. The order is important. A mistake in the order can leave a ghost.

Analogy: closing a bank account First the bank blocks the card (so nobody can use it any more). Then it shreds the paper files. Last, it removes you from the customer list. If the bank stopped after step one, your card is still blocked. You are safe, and the bank can finish later.

What if a step fails?

The identity row is a tombstone, but no row is deleted yet. A sync with this player's token gets 410 account_deleted. The Lambda creates no new user ID. The app retries the whole call. All steps repeat safely, so it finishes the job.

The games are gone, but the Clerk user still exists. The player can still sign in at Clerk. But every sync answers 410, because of the tombstone. A retry of the call runs step 3 and finishes. The tombstone keeps the userId on purpose: a retry needs it to find the rows.

Clerk is down. The call answers 500. The player stays tombstoned, which is fine: they asked for deletion. The app can retry while its Clerk session is still valid. The session ends only with the last step.

Think about the reverse order. If the Clerk user were deleted first and the call then failed, the player could no longer get a token. Nobody could finish the delete. The tombstone also blocks a trap: an old token (they live 60 seconds) could otherwise make a brand new account for the same sub. The tombstone lives 30 days, longer than any token, then DynamoDB removes it.

The same story on the phone

The phone side lives in createAccountLifecycle (mobile/src/account/accountLifecycle.ts). It has one rule: the server goes first. The phone changes nothing until the server confirms. Step through it.

1. Pause the sync

A sync run that gets 410 during the delete would clean up a second time. So sync.pause() aborts the request in flight and waits until the run has stopped.

2. Ask for a fresh token

The app asks Clerk for a token that skips the cache. If Clerk gives none, the app answers "offline". Nothing changes and the player can try again.

3. Call the server (with retries)

The app sends DELETE /v1/account. It keeps the same token for up to 2 retries (DELETE_RETRIES), one second apart. Why the same token? After the server deleted the Clerk user, Clerk cannot give a new one. The client waits 35 seconds, longer than the 30 second Lambda, so a retry never runs next to the first call.

4. Delete the local entries

Only after a 2xx does the phone act. history.deleteOwner(owner) removes every row of that owner (live or soft-deleted) and the sync state, in one transaction. It is the only hard delete of the history in the whole app.

5. Sign out of Clerk

account.signOut() never rejects. If it fails, the app sets a flag in the Keychain (pendingSignOut) and signs out silently at the next start.

6. Forget the owner

The owner cache becomes null for the rest of the session and the account is marked deleted. The player sees one alert. A lost answer is handled too: if the answer was lost but the next call gets 401 inside the same open screen, the app counts it as deleted, because the server must have removed the Clerk user.

The 410 reaction: a delete from another device

Phone B deletes the account. Phone A does not know. At its next sync, phone A sends a valid token (Clerk sessions can outlive the user for a while). The server finds the tombstone and answers 410 account_deleted. The sync service ends the run with the result deleted. It sets a deletedOwner so no further trigger starts a run, and it calls onAccountDeleted(owner) of the lifecycle. That function uses the same cleanUpOnce as the delete screen, so a delete and a 410 at the same time clean up exactly once. The player sees one alert, "deleted elsewhere".

Why does the server turn the identity row into a tombstone before it deletes the games?

The tombstone blocks the player at once: sync answers 410 and no new user ID is ever created. A later failure leaves a safe state, and a whole retry finishes the job.

7. The history sync, in depth

Now the heart of the chapter. The goal is simple to say: every finished game ends up on every device of the player, and a failure never hurts the game. It is hard to do right when phones go offline, requests get lost and two phones act at once. The design in ADR-028 and the concept history-sync solves it with a few small ideas. We take them one by one.

Idea 0: the history almost never changes

A finished game is a fact. It does not change after the finish. The only change is a soft delete (the player removes a game from the history, and the app sets deleted_at). That makes merging easy. Two phones add different games, and the union is the answer. There are no "edit wars". This is why only the finished history syncs, and not the game in progress or the settings.

Idea 1: the waiting list (an outbox)

The phone needs to know which entries the server does not have yet. A common design is an outbox: a list of things that wait to be sent. In the docs this is the waiting list. It is not a separate table. It is a query on game_history: 

owner_id = ? AND (pushed_at IS NULL OR pushed_at <> updated_at)

That is WAITING_WHERE in mobile/src/storage/historySql.ts. The trick is the column pushed_at. It does not hold a clock time. It holds the value of updated_at that the server accepted.

Why not a simple boolean "synced"? Imagine the push is in flight. The player deletes that game meanwhile. The server answers "accepted". A boolean would flip to true and hide the new change forever. With pushed_at, the app marks an entry pushed only where updated_at still equals the value that was sent (MARK_PUSHED_SQL in historySql.ts). The delete changed updated_at, so the entry stays on the list and goes up in the next run. No phone clock is compared either, only equality.

Idea 2: one call, push then pull

A sync is one HTTP call, POST /v1/sync. The body carries up to 100 waiting entries and the last cursor. The server first pushes (stores the entries) and then pulls (reads what the other devices stored). One round trip does both. Because the push comes first, the answer already includes the player's own changes, which the app then ignores because they are equal.

Note the division of work. syncRun.ts owns the network, the rounds and the retries. HistoryRepository.applySyncPage owns the database. It does three things in one transaction: it marks the pushed entries, writes the downloaded entries and saves the cursor. If the app dies in the middle, either all three happened or none did. So the cursor never moves ahead of the data it points to.

Idea 3: the cursor, and pages

How does the server know which games a phone has not seen? It cannot trust the phone's clock. So the server stamps every stored entry with its own time, syncedAt. The phone remembers how far it has read: the watermark, the highest syncedAt it pulled. The server packs the watermark into a cursor. The app stores it as an opaque string and never reads inside it. That keeps the format free to change on the server.

Inside, the cursor is base64url of a small JSON: { v: 1, since, after } (backend/api/src/cursor.ts). since is the watermark. after is a DynamoDB LastEvaluatedKey, used only while a long pull is in the middle of paging. A null cursor means "give me everything": a new device, a new account, or a recovery.

A phone can have thousands of games, and one answer holds at most 500. So the pull comes in pages. While a page is full, the response has more: true and a cursor with the same since and the after key of the last row. The app simply calls again.

The empty last page (a famous edge case)

DynamoDB returns a LastEvaluatedKey when a page stops at exactly the limit, even if no row follows. So a pull of exactly 500 rows says more: true. The next call reads zero rows. Then nextCursor() must still advance: it takes since from the first of these that exists: the last row read, the after.syncedAt of the request, the old since. Without the middle rule, the watermark would fall back and the next sync would read the same range again. The simulation below reproduces this: its page size is 2, so you can see it.

The server also checks the cursor. A cursor it cannot decode, or an after whose partition is not the caller's, gives 400 invalid_cursor (assertCursorOwner, assertCursorRange). So nobody can steer a query into another player's partition. The app answers by clearing the cursor and doing one full pull.

Idea 4: idempotency, so a lost answer is harmless

Networks lose answers. The server may store your games and the phone never hears about it. What now? The phone just sends the same entries again. This is safe because the call is idempotent.

  • Every history entry has a UUID. The row key is GAME#<uuid>. A second write with the same id targets the same row.
  • The write has the condition attribute_not_exists(pk) OR updatedAt < :updatedAt. An equal or older version cannot overwrite. It is a no-op.
  • A no-op still counts as accepted. The server says "I have this or something newer". So the retry gets the same acceptedIds, and the phone takes the entries off the waiting list.

Idea 5: conflicts are tiny

Two phones can only disagree about the soft delete of the same game. The rule is simple: the entry with the higher updatedAt wins. The server enforces it in the write condition. The phone enforces it when it applies a downloaded entry (upsertRemote): it writes a downloaded entry only when it is new, or its updatedAt is newer. When the times are equal, it only sets pushed_at. Remember the two different clocks:

QuestionWho answersWhich clock
Which version of one game is newer?Compare updatedAtThe device clock (set when the player acts)

Idea 6: adopting the games from before sign-in

A player may have played for a month signed out. Those games have no owner. At the first sign-in the app asks once: "Add the games on this phone to your account?" (runAdoptStep in mobile/src/sync/adoptStep.ts).

  • Add games: answerAdopt(owner, true) gives every live ownerless entry the owner, in one transaction. Then they are on the waiting list and go up.
  • Not now: the entries stay ownerless. The app remembers the answer (adoptAsked:<owner> in sync_state) and never asks again for that account.
  • No request leaves the phone before the answer. A player with no ownerless games is not asked at all.

The app never moves the entries of another owner. It adopts only entries without an owner.

Idea 7: quiet triggers, quiet failures

iOS does not let an app run in the background freely, so there is no background timer. The sync runs on four triggers (useSyncTriggers.ts, SyncProvider.tsx):

TriggerWhenNote
game-endThe storage tells the service a game was saved (GameStorage.subscribe)Skipped when nothing waits. game/ imports nothing from sync/
foregroundThe app becomes activeRespects the backoff
networkThe connection returns while the app is openSkips the backoff wait
sign-inAfter sign-in and the adopt promptSkips the backoff wait

The service is single-flight: one run at a time. A trigger during a run does not start a second run. It only asks for one more run afterwards, however many triggers came. Think of one elevator: many people press the button, but it makes one trip at a time.

A failure is silent. No banner, no spinner, no error dialog. The player sees at most a muted line on the stats screen, "Synced 5 min ago", when signed in. After a failure, the next trigger is ignored until a wait is over: 30 seconds, doubled with each failure, at most 15 minutes. A Retry-After of a 429 counts if it is longer.

Limits inside one run
  • A run stops after 20 requests (MAX_ROUNDS) with the result partial. That is not a failure. The service then starts at most 5 follow-up runs (MAX_FOLLOW_UP_RUNS).
  • From round 8 the run sleeps 1.1 seconds before each request (PAUSE_AFTER_ROUND), so a long pull stays under the API throttle of 1 request per second.
  • The run marks only the accepted entries that it sent. It stops when the server accepts none, so a full daily count cannot make an endless loop.
  • An entry that breaks the sync contract, or a database CHECK, is dropped and logged. It never blocks the cursor. A local entry that breaks the contract stays on the list and the app never deletes it. If more than 900 such entries sit at the head, they block the valid ones. This limit is accepted for version 1.
  • A sign-out or an account switch aborts the request in flight (AbortController). A run of an old session cannot change the status or the backoff of the new one (the isCurrent() guard).

A game was pushed, but the answer was lost. What happens at the next trigger?

This is idempotency: the id is the row key, the write is conditional, and a no-op counts as accepted. The phone then takes the entry off the waiting list.

8. Two phones and a server (simulation)

Now play with it. Below are two phones, A and B, and the server. The same player owns both. The logic follows the real rules: the waiting list, the server syncedAt clock, the conditional write, the cursor with an overlap, and pages. To make the effects easy to see, the sizes are small: a batch of 2 entries, a page of 2 changes, an overlap of 1 server tick, and an optional daily cap of 3. The real values are 100, 500, 5 minutes and 200.

Try this
  1. On A press Finish a game twice. On B press it once. Nothing has moved yet. The entries wait on their phones.
  2. Press Sync on A. Watch the log: push, then pull. The server stores two rows.
  3. Press Sync on B. B pushes its game and pulls A's two games. Press Sync on A again: it gets B's game.
  4. Tick Lose the next answer, finish a game on A, and Sync. The server stores it, but A hears nothing. Sync again: the server says "noop" and A takes it off the list.
  5. Take B offline, delete a game on A and on B, sync both, and see which delete wins.
  6. Tick Daily cap of 3. Finish 5 games on A and sync. See what stays on the list. Press New UTC day and sync again.
What the simulation leaves out

It does not model the owner or the adopt prompt, the token, the 401 retry, the backoff, or the failure of the app in the middle of a transaction. It uses one shared counter for the device clock, so two phones never disagree about time. The real clocks can differ, which is exactly why the app never uses the device clock to decide what is new. The real code is in mobile/src/sync/syncRun.ts and backend/api/src/{sync,push,pull,cursor}.ts.

9. The sync contract: one schema, two codebases

The app and the Lambda talk in JSON. Both sides are TypeScript. What if the app sends hintsUsed and the Lambda expects hints_used? The sync breaks, and only in production. The fix is to write the shape once. That is the package shared/sync-contract/. Both the app and the Lambda import it. It depends only on zod.

Analogy: one printed form Two offices exchange paper forms. If each office prints its own form, the boxes will not match. So they agree on one master form and both print from it. The schema is the master form. It also works as a checker: a form with a missing box goes back to the sender.

A zod schema does two jobs. At run time it validates a value. At compile time, z.infer turns it into a TypeScript type. So the type and the check can never drift apart. This is the real schema of one history entry, shortened: 

export const historyEntrySchema = z.object({
  schemaVersion: z.literal(1),
  id: z.uuid(),
  level: z.enum(['easy', 'medium', 'hard', 'expert']),
  source: z.enum(['generated', 'scanned']),
  result: z.enum(['won', 'lost', 'abandoned']),
  seed: z.int().min(0).max(MAX_SEED).nullable(),
  playedMs: z.int().min(0),
  mistakes: z.int().min(0),
  hintsUsed: z.int().min(0),
  finishedAt: utcTime,   // ISO 8601, UTC, exactly 3 decimals
  createdAt: utcTime,
  updatedAt: utcTime,
  deletedAt: utcTime.nullable(),
})

Because API Gateway sends its own body for 401 and 429, the app reads the status code first (resultOf in syncApi.ts). The message text is fixed and never repeats the request or any personal data.

What is not on the wire

Two things never travel. The owner is not in the body. The server takes the player from the token. And syncedAt is not in the entry. The server stamps it itself, because only the server clock may decide what is new. The phone converts a database row to a wire entry with toWireEntry (mobile/src/storage/wireEntry.ts) and drops the owner and pushed_at on the way.

Why the app checks each change separately

A strict check of a whole page would reject 500 good entries because of one bad one. So syncApi.ts parses the answer with syncResponseSchema.omit({ changes: true }) and keeps changes as a raw array. Then applySyncPage checks each change on its own (parseChanges). A bad change is dropped and logged, and the cursor still moves. On the way up, nextBatch leaves out local entries that do not meet the contract (meetsContract), so one broken row cannot make every request a 400.

10. Inside the Lambda: from request to DynamoDB

Let us follow one POST /v1/sync through the real code. The files are in backend/api/src/. Use the arrow keys or the buttons.

1. The request reaches API Gateway

The route throttle comes first: 1 request per second, burst 10. Over the limit gets 429 and costs no Lambda run.

2. The JWT authorizer

Signature, issuer, audience and expiry are checked. A bad token gets 401 here. Only a request with valid claims goes on.

3. handler.ts and route.ts

handler.ts is the only file that imports sst. It builds the dependencies (SyncDeps: the DynamoDB client, the table name, a clock, a UUID maker, a logger, a lazy Clerk client) and calls route(). The clients live at module scope, so a warm Lambda reuses them. route() wraps the call in observe() (timer, log line, error to response) and switches on routeKey. All the dependencies are passed in, so tests can replace them.

4. sync.ts: read and check the input

It takes sub from the claims (subOf), parses the JSON body, and checks it with syncRequestSchema.safeParse. A body that does not fit gives refuse('invalid_request'). A Refusal is thrown, so the call stops before any write. Then decodeCursor turns the string into an object.

5. identity.ts: who is this?

findOrCreateUserId does a consistent GetItem on IDENTITY#clerk#<sub>. Found: return its userId. A tombstone throws AccountDeleted (410). Missing: PutItem with attribute_not_exists(pk). If a parallel request won the race, read again.

6. Check the cursor against the player

assertCursorOwner refuses an after key outside this player's partition. assertCursorRange refuses an after that lies before the read window. Both give invalid_cursor. All this happens before the first write.

7. push.ts: write each entry

For each entry, in request order, one TransactWriteItems runs three things at once (see the box below). One server time, deps.now(), stamps the whole request. The outcomes are counted: stored, noop, capped, conflicts.

8. pull.ts: read the changes

A Query on the index bySynced with ConsistentRead: true, so the push of this very request shows up. Key condition: pk = :pk AND syncedAt >= :from, where from is the watermark minus 5 minutes. Limit 500, ascending. nextCursor() then makes the new cursor.

9. Answer

The Lambda returns { acceptedIds, changes, cursor, more } with status 200. observe() writes one JSON log line from an allow-list: request ID, route, status, our user ID, counts, duration. It never logs the event, the token, the sub or an email. On an unexpected error it logs only the error name, because a DynamoDB message can contain a key, and the identity key contains the sub.

The push transaction in detail (push.ts)

One TransactWriteItems per entry holds three items. All three succeed together, or none is written. That is how the daily count stays exact even when two requests of one player run in parallel.

ItemOperationConditionIf the condition fails
gamePut the game row, with syncedAtattribute_not_exists(pk) OR updatedAt < :updatedAtnoop. The server has this or newer. Counted as accepted
countAdd 1 to COUNT#<today>.writeswrites < 200 (or no row yet)capped. Nothing stored. Not accepted. It stays on the phone's list
identityCheck onlyattribute_not_exists(deletedAt)Throw AccountDeleted (410). A delete that ran after the read still stops the write

DynamoDB tells which item failed in CancellationReasons, in the same order as the items. The code keeps that order in one list (ITEM_ORDER) and uses it twice. A TransactionConflict (another request touched the same row) gets 2 retries with a random delay of 20 to 80 ms. After that, the entry stays on the phone's waiting list. The loop never stops at the cap, so a later no-op in the same request is still accepted.

11. The DynamoDB table, drawn

DynamoDB is not SQL. You decide how you will read first, and then you design the keys. Every row has a partition key (pk) and a sort key (sk).

Analogy: a filing cabinet The pk is the label on the drawer. All the papers of one player sit in one drawer. The sk is the order of the folders in the drawer. Opening one drawer is fast. Asking "give me everything in all drawers that has property X" is slow and costly, so you avoid it.
RowpkskNotes
IdentityIDENTITY#clerk#<sub>IDENTITYMaps a login to userId. A tombstone adds deletedAt and a 30-day expiresAt
GameUSER#<userId>GAME#<uuid>The entry without its id (the id lives in sk), plus syncedAt
Daily countUSER#<userId>COUNT#<yyyy-mm-dd>writes. Expires at the start of its UTC day plus 2 days
ScanUSER#<userId> or CONTRIB#<contributorId>SCAN#<scanId>The scan record. gsiPending is PENDING until pulled. Expires after 365 days

Two indexes, both sparse

A secondary index is another way to order the same rows, like the index at the back of a book. A sparse index holds only rows that have the indexed attribute.

  • bySynced is a local index: same pk, sort key syncedAt. Only game rows have syncedAt. So a pull reads only games, in the order they were stored. A local index also allows a consistent read. It must exist from the first deploy, because DynamoDB cannot add a local index later.
  • byPending is a global index: gsiPending and createdAt. Only scan rows that wait for the developer have gsiPending. The pull-scans tool lists new scans without reading the whole table.
Question the backend must answerHow
Who is the player behind this token?Get IDENTITY#clerk#<sub>
What is new for this player since the cursor?Query bySynced with pk = USER#id and syncedAt >= from
Has this player hit the daily cap?Update COUNT#today with a condition, inside the push transaction
Delete everything of a playerQuery the partition USER#id and delete each row in pages and batches
Which scans wait for the developer?Query byPending for PENDING
Remove old dataTTL on expiresAt (tombstones, daily counts, scans)
TTL, in one sentence A table has one TTL attribute, expiresAt, a number in epoch seconds. DynamoDB removes an expired row some time after it expires (not on the exact second). So the tombstone, the daily count and the scan row share it.

12. The scan collection: helping the model learn

Chapter 4 explained how a scan works on the phone, and chapter 5 how the model learns. This part is the road between them. A scan record is the data of one finished scan: a cropped photo, the four corners, the model's answer for each of the 81 cells, the final grid after the player's corrections, and a flag per cell edited that says if the player changed the answer. A corrected cell is a free, fresh label.

Rule SUD-02 (changed by ADR-030) Camera frames and cell images MUST NOT leave the device. A photo may leave only through the setting "Help improve the app". The setting is on by default, the player sees a notice before the first upload, and the player can turn it off at any time. An image that the player imports from the photo library never leaves the phone, also when the setting is on.

Step through the road, from the correction screen to the developer's laptop.

1. The setting and the notice

The setting SHARE_SCANS_SETTING (mobile/src/scanShare/scanShareSettings.ts) is on unless the player turned it off. Before the very first upload, a notice sheet explains what leaves the phone. "Got it" lets the waiting scans go (acceptNotice). "Turn off" clears the queue (declineNotice). The uploader checks the notice flag before every scan.

2. Leaving the correction screen

When the player leaves by any route except Retake, the screen calls enqueueScan. It never throws and never waits for the network (SUD-01). It queues nothing when sharing is off, when the photo is missing, when the scan came from an imported image, or when the record breaks the contract. The original photo is deleted in every case.

3. Crop and build the record

cropPhoto.utils.ts cuts the upright photo to the grid plus a margin of 8% (CROP_MARGIN), at most 1600 pixels on the long side, and encodes it again as a JPEG. That removes EXIF and the location. It tries quality 0.85, then 0.7, 0.55, 0.4 until the file is at most 1 MB. buildRecord.utils.ts adds the corners, the 81 cells (digit and kind probabilities, final digit and kind, edited), the app and model versions and the random contributor ID of this device. It checks the result with validateScanRecord from shared/scan-contract.

4. The local queue

The record goes into the table scan_queue in its own database file (scan-queue.db), so a scan that waits for days never touches the game storage. The photo is saved in a folder next to it. INSERT OR IGNORE on scan_id makes a double enqueue harmless. A row stays until the server takes the scan or rejects it.

5. The uploader sends the record

drainQueue sends the due scans one by one and stops at the first failure, because the phone is probably offline. For each scan, createUploader posts POST /v1/scans with the record as the body and two headers: the shared app key (x-app-key) and the photo length (x-jpeg-bytes). A signed-in player also sends the bearer token, so the scan can be linked to the account.

6. The scans Lambda

scan.ts checks the app key in constant time (appKey.ts), validates the record, and checks the length (1 to 1,000,000 bytes). With a token it verifies the JWT itself (token.ts, library jose), because this route has no authorizer. putScan writes one row with attribute_not_exists(pk), so a repeat of the same scanId makes no second row. Then it returns a presigned URL: a one-time S3 address that signs the exact Content-Length.

7. The photo goes straight to S3

The phone sends PUT with the JPEG to the presigned URL. S3 refuses a file of another size. The Lambda never touched the photo bytes, which keeps it small and cheap. On success the queue row and the local photo are deleted. On failure the scan waits with backoff: 60 seconds, doubling, at most 6 hours. A 401 or 410 with a token makes the uploader retry once without the token: the scan then counts for the device, not for the account.

8. Later, on the laptop

The developer runs just pull-scans. It reads the PENDING rows through byPending and downloads the photos to ml/dataset/ (never committed, SUD-08). Then a person checks each outline and each digit in the labelling app. Only verified cells train the model. The row and the photo expire after 365 days.

Why a presigned URL and a separate Lambda? A photo is up to 1 MB. If it went through the Lambda and API Gateway, it would cost more and slow the sync. With a presigned URL the phone talks to S3 directly, and the Lambda only hands out the permission. The route has no authorizer, so anyone could call it. A separate function with its own tight throttle means abuse of this route cannot starve the sync. The shared app key is only a speed bump, not a secret (SUD-11).

Deleting a scan

A player who is signed in and deletes the account also loses the scans that were sent while signed in (the delete removes the rows and the photos). Scans that were sent while signed out stay under the contributor ID. The player asks for those by email, and quotes the contributor ID that shows in the footer of Settings. A retry after a lost response can leave two rows for one scan. Deletion does not undo training that already used a scan.

Which of these can leave the phone through "Help improve the app"?

Only a finished scan from the camera, cropped and re-encoded, can leave. Camera frames, cell images and imported images never leave (SUD-02).

15. How the backend is tested

A backend that you cannot test locally is a backend you fear to change. The tests come in layers. The cheap ones run often. The expensive ones run when the risk is real.

CommandRuns
pnpm --filter @sudoku/sync-api testThe unit tests of the Lambda. just test-ts runs them too
just test-apiThe DB tests. It starts DynamoDB Local in Docker first
just dynamodb-downStops and removes the DynamoDB Local container
just testBoth of the above and every other test of the repository

DynamoDB Local runs in one container named sudoku-dynamodb on port 8000. Every worktree shares it. Each DB test file creates its own table from tableDesign.ts, the same file that the real deploy reads. So the test table and the real table cannot differ by accident.

Safety rails in the tests
  • The tests refuse an endpoint that is not local, and they use fixed local credentials. A test can never write to the real account.
  • DynamoDB Local does not delete expired rows, so the tests check the value of expiresAt only, not the deletion.
  • Pure logic has its own tests without a database. nextCursor, readStart and the cursor checks are pure functions of their input.
  • The infra files with no SST globals (config.ts, backend-settings.ts, budget-alerts.ts, the OIDC policy) are tested with node --test. A test also checks the workflows.
  • The kill switch takes its AWS calls as dependencies (KillSwitchDeps), so a test can make any step fail and check the report.
  • On the phone, the sync service takes a fake clock, a fake sleep and a fake API. Backoff and retries run in milliseconds in a test.
Why every dependency is passed in Look at handler.ts: it builds a SyncDeps object (database, clock, UUID maker, logger, Clerk, photo store) and gives it to route(). Only handler.ts imports sst. Everything else takes its dependencies as arguments. That is why a unit test can run the whole sync with a fake database and a fixed clock, and why the same code runs unchanged against DynamoDB Local.
