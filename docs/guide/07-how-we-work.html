Chapter 7

Quality and how we work

A project that one person builds with many agents needs rules that a machine can check. This chapter shows how the project defines good, how it tests, how it guards its own structure, and how a change travels from an idea to the develop branch.

Analogy Think of a bakery with one baker. The baker cannot taste every loaf at every hour. So the baker writes down what a good loaf is, installs ovens with timers, and puts a checklist on the wall. This chapter is that wall.

What “good” means here

The problem. “The scanner works well” means nothing until someone says how well, and on what. Without a number, two people argue and nobody can tell whether a change helped.

The project solves this with a quality tree and numbered scenarios. The tree has five goals. Each goal has scenarios with a target you can measure. The source is chapter 10 of the architecture docs.

Why the target counts whole grids

One wrong digit breaks a puzzle. So the main target is not “most cells right”. It is “all 81 digits right”. This metric is the grid-exact accuracy. It is much harsher than the per-cell number. A small drop in per-cell accuracy drops the grid score fast, because the cell chances multiply: p81.

Why this way? The 95 % grid target (QR-01) forces a per-cell target of 99.94 %. The number looks extreme. But it is the honest translation. The current model has 98.71 % on 1,550 real test cells, so about 35 % of grids would be fully right. The correction screen exists to close this gap: it marks the least certain cells so that the player checks them.
A target needs enough data The targets gate only when the dev split has at least 40 newspaper scans and 20 book-page scans. Below that, a percentage means little. The numbers are reported but do not block anything.

How the project measures

The problem. Some targets are about speed on a real phone. A laptop cannot tell you the frame rate of the camera loop on an iPhone.

Two kinds of measure exist. A test runs on every push and gives a pass or a fail. A measurement session happens by hand, on the reference iPhone, now and then. The result goes into a record.

The development variant writes lines that start with [measure] and the scenario ID. It does this also in its Release build. A Release build matters, because a debug build is slower and would give false numbers. The steps are in the measurement guide. The results go into the quality measurements record.

Be honest about open numbers On 2026-10-22 the method and the Mac number for QR-12 were in the record. The iPhone results were still marked (open). Read the record before you claim that a scenario passes.

The test pyramid

The problem. Each part of the code tests in a different way. The game rules are plain TypeScript. The scanner needs a camera and native code. The model is Python. One tool cannot test all of them well.

The analogy. A restaurant checks quality at many levels. The cook tastes each sauce (small, fast, many). The chef tastes the full plate (fewer). A guest reviews the whole evening (rare and costly). Tests work the same way. Many cheap tests at the bottom. A few costly ones at the top.

ADR-010 defines the layers. Click a layer to read what it tests, how to run it, and where it runs.

Click a layer to read about it.

End to end: Maestro flows (layer 5)

Problem: unit tests cannot show a broken navigation, a native module that does not load, or a game that a restart loses.

What: YAML flows in mobile/e2e/ (finish, levels, resume, scan, theme) drive the Release app on the iOS Simulator. They find elements by testID. Each flow clears the app data first.

Run: just ios-simulator, then just e2e. The flows use their own simulator, “Sudoku E2E iOS 26”.

In CI: only on a manual step. A macOS minute costs ten times. One run costs about 200 of the 2,000 monthly minutes. Add the label run: e2e to a pull request. The flow scan needs the real model, so CI skips the tag model.

Fixture runner (layer 3)

Problem: the scanner uses VisionCamera, fast-opencv and fast-tflite. They do not run in Node or Jest. A mock would test the mock, not the scanner.

What: a screen in development builds only. It reads fixture photo files instead of the camera. It runs detectGrid and recognise on each photo. It reports corner error, intersections found and grid-exact against truth.json. It writes the cell images and scanner.json that the promote gate reads (ADR-007).

Run: by hand, on the device. Run it before a promote, before and after a native-module upgrade, and when the capture stage changes.

Status: TD-05 in chapter 11 says the runner and the public fixture set are not built yet. Today, no test runs the real scanner on fixture photos.

App logic: Jest (layer 2)

What: screens, state, storage and the scan screen. Jest and React Native Testing Library render the components. The scanner sits behind its interface and is a fake here.

Why it works: the app reaches the scanner only through src/scanner/index.ts (SUD-05). So a fake is easy. The same rule keeps the interface small.

Run: pnpm -r test, which just test-ts includes. CI runs it on every pull request that touches TypeScript.

Game logic: Vitest (layer 1)

What: @sudoku/core: rules, solver, generator, grader and hints. It is pure TypeScript with no I/O (SUD-04). So the tests are fast and need no phone.

Also here: two measuring tools that use the same package. just bench-core times nextSteps and the generation of each level (QR-12). just technique-coverage measures how many generated puzzles the techniques solve.

Run: pnpm -r test. CI runs it on every pull request.

pytest for ml/ (layer 4)

What: preprocessing parity against shared/fixtures/preprocess/, dataset manifest checks (SUD-10), a training smoke test and the classifier score on committed cell images.

Why parity matters: Python and the app must cut and scale a cell the same way. The reference pairs are the shared truth. Both sides test against them. See chapter 5.

Run: just test-ml. CI runs it when ml/, the model contract or the fixtures change.

DynamoDB Local

Problem: a mock of the database would hide real query mistakes.

What: the sync-api tests run against the real DynamoDB engine in a Docker container (amazon/dynamodb-local:3.3.1, ADR-027). All worktrees share one container.

Run: just test-api. It runs just dynamodb-up first. Stop the container with just dynamodb-down. CI starts the same image as a service. Keep the tag in the workflow equal to dynamodb_image in the justfile.

node --test for the tools

What: the small tools of the repo have tests too. The custom oxlint plugin, the icons tool, the layout check, the delete-scans tool and the infra files each have *.test.mjs or *.test.ts files. The infra test also fails when a workflow uses a floating action tag.

Why: a guard that has no test can fail silently. A rule that never fires looks the same as a rule that works.

Run: just test-ts runs them after the Vitest and Jest suites.

Why not an iOS build on every push? ADR-010 first said “no iOS build in CI”. A macOS runner is slow, and the free plan counts a macOS minute ten times. An amendment on 2026-10-22 added a build for the simulator. It runs only when a native input changes (mobile/package.json, app.json or app.config.ts). The reason: an Expo or native-module upgrade can break the native build, and risk R-08 says exactly that.

The scanner uses native modules. Which test layer runs the real scanner on photos?

Jest fakes the scanner behind its interface, so it tests the app logic only. Vitest has no native modules. Only the fixture runner runs the real native code on real photos. It is a manual layer (ADR-010).

What CI does on a pull request

The problem. People forget steps. A check that depends on memory fails when the person is tired. CI is a robot that runs the checks for every pull request, on a clean machine.

The workflows live in .github/workflows/. Each has a paths filter. A pull request that changes only Markdown does not start the TypeScript job. This saves time and, for macOS, real money.

After the merge: the deploy lanes

Why a manual run is the approval The repository is private on the free GitHub plan. That plan has no environment with a required reviewer. Only the owner has write access, so starting the run is the approval. The AWS role trusts only one workflow file on develop. GitHub stores no AWS secret: the workflows use a role through OIDC. See ADR-010 (amendment 2026-10-15) and the backend infra README. Chapter 6 covers the backend itself.
Every action is pinned Each uses: line names a full commit SHA, not a tag like v4. A tag can move. A SHA cannot. A test in backend/infra fails when a workflow uses a floating tag.

The guards: lint, format and boundaries

The problem. A rule in a document is only a hope. “The game must not use the scanner” is easy to break by accident with one import line. A rule that a machine checks cannot be forgotten.

The analogy. A document rule is a sign that says “no entry”. A machine rule is a locked door. This project uses locked doors for every rule that it can.

Tool: dependency-cruiser. Config: .dependency-cruiser.cjs. Run: just boundaries (it calls pnpm boundaries).

It reads every import in the code and fails when an import crosses a forbidden line. Each rule has a name that points to its source. Some examples from the config:

Rule nameWhat it forbids
sud-04-core-has-no-dependencies@sudoku/core imports no package, no Node builtin, no React Native
sud-03-game-does-not-use-scannerThe game imports nothing from the scanner
sud-05-scanner-has-one-entry-pointThe app reaches the scanner only through src/scanner/index.ts
adr-027-app-does-not-import-servicesThe app does not import backend code
a-feature-does-not-import-a-sibling-featureFeature folders stay independent
no-circularNo import loop

ADR-010 says that each rule was shown to fail on every kind of violation that it claims to cover. A rule that was never seen to fail is a rule that may not work.

Tool: tools/layout/check-layout.mjs. Run: just check-layout.

It enforces SUD-12: the repository root holds only the folders and files that ADR-029 lists. The folders are .github, backend, docs, ml, mobile, shared, tools and web. A stray file at the root fails the check.

Pitfall Add a new root file or folder? Write or amend ADR-029 first, then update the list in the check. The order matters (AGENTS.md rule 2).

Tool: oxlint with our own plugin, tools/oxlint/sudoku-plugin.mjs. Run: pnpm lint (inside just lint-ts).

The plugin holds rules that only this repository needs:

  • No colour literal. Only mobile/src/theme/ holds raw colour values (ADR-015). A #fff, an rgba() or the word white anywhere else fails.
  • No literal player text. Text that the player sees or hears comes from the catalogues in src/i18n/messages/ (ADR-033). Use intl.formatMessage.

Warnings fail the run, because the command is oxlint --deny-warnings. The plugin has its own tests, so the rules do not rot.

Tool: oxfmt. Run: just format to fix, just format-check to only check.

The formatter ends style debates. just lint-ts runs the format check first, so an unformatted file fails CI. oxlint replaced ESLint in ADR-010: one small JSON config, no plugin conflicts with Expo, and a run in well under a second.

Tool: ruff. Run: just lint-ml.

It runs ruff check and ruff format --check on ml/. Ruff also enforces two comment rules from AGENTS.md: no commented-out code, and no blanket noqa.

Link check: tools/check_links.py, run by just docs-check. It reads every Markdown file in the listed folders. It fails when a relative link points to a file that does not exist. It skips code blocks, inline code and generated folders (node_modules, ios, android).

Workflow lint: just lint-workflows runs actionlint on the files in .github/. It needs a local install (brew install actionlint). CI has its own lane for it.

just lint runs all of these together: lint-ts, boundaries, lint-ml and check-layout. Run it before you open a pull request.

A developer adds a file called notes.txt to the repository root. Which check fails?

tools/layout/check-layout.mjs compares the root with the list from ADR-029. dependency-cruiser reads imports only. The link check reads Markdown links only.

The justfile: a command finder

The problem. The project has Node, Python, Xcode, Docker and AWS commands. Nobody remembers all the flags. just puts one short name on each recipe. Run just --list to see all of them. Every recipe has a comment line above it that explains it.

Pick a goal. The finder shows the command and what it does. All commands come from the real justfile.

There is no promote command yet ADR-007 describes a promote gate. The justfile has no promote-model recipe today. Technical debt TD-04 records this. just install-model copies a model without fixture scores. This is the one named exception to SUD-06.
Why the AWS recipes use a long prefix

The recipes deploy-api, diff-api, api-on and others start with env -u AWS_ACCESS_KEY_ID … AWS_PROFILE=sudoku. SST reads AWS_* variables before it reads its own profile. The prefix removes them. So only the personal profile sudoku is used. A script backend/infra/check-account.ts then confirms the account. This stops an employer account from receiving a deploy by mistake (ADR-027).

The developer workflow

The problem. Many agents and one developer work on the same repository. Without a fixed path, work gets lost, branches clash and nobody knows why a change exists.

The analogy. A kitchen ticket rail. Each order is a ticket. A cook takes one ticket, cooks it, and a second person checks the plate before it leaves. The ticket here is a GitHub issue.

Click Next to follow one change from idea to merge.

1. Start from an issue

Every change starts from a GitHub issue, made with gh. If none exists, the agent proposes one. The agent does not create it without the developer's approval. An issue has one type: label, one area: label and a milestone from M0 to M4. An open issue also has one priority: label.

2. Get the plan approved

Work on an issue starts only after its implementation plan is approved. The plan states the approach and the files. This is where a wrong idea is cheap to stop. If a change would break a SUD-xx rule, the agent stops and says so. It does not work around the rule.

3. Make a branch from develop

The name is <type>/<issue>-<slug>, for example feature/12-technique-solver. Branch from origin/develop. develop is the integration branch. main is stale.

4. Commit in small steps

Messages follow Conventional Commits: feat:, fix:, docs:, chore:. Add the issue number, for example feat(core): add naked singles (#12). A model promotion is its own commit. An agent does not commit or push unless the developer asks.

5. Open a pull request

The body of the template has Closes #, a short “What changed”, a “How it was tested” section that names the layers of ADR-010, and a checklist. The pull request that meets the last open criterion of an epic says Closes #<epic>. Every other pull request of the epic says Part of #<epic>. Do not close issues by hand.

6. A second agent reviews

Before the merge, a second agent reviews the pull request without the context of the first session. Fresh eyes catch what the author no longer sees. Fix the findings, or answer them in the pull request. Tick the acceptance criteria in the issue when you meet them. When the work proves or changes a decision, update the ADR in the same pull request.

7. Merge into develop

The pull request targets develop. The developer decides when it merges. “Just merge”, or a passed iPhone test, means merge now. A merge that changes a backend file starts deploy-api-dev.

Rule: the developer decides Agents do not commit or push unless the developer asks. Agents do not create issues without approval. Agents do not change an accepted decision in code alone: write or amend an ADR first.

Which branch name follows the rule?

The format is <type>/<issue>-<slug>. The type says what kind of change it is. The issue number links the branch to the reason for the work.

The documentation system, in short

Chapter 1 covers the architecture docs in detail. Here is only what you need for daily work.

  • The docs follow Arc42: numbered files 01- to 12- in docs/architecture/. Each starts with status: DRAFT or status: ACCEPTED.
  • 00-DECISIONS.md is an index. It has one line per constraint or decision. The reasoning lives in the source that the line links to.
  • An ADR is Proposed until it is validated, then Accepted. To replace one, write a new ADR that says “Supersedes ADR-NNN”. Do not rewrite the old decision.
  • When you add or change a decision, update 00-DECISIONS.md and 09-architecture-decisions.md in the same change.
  • Diagrams in the repo docs are Mermaid. Check every relative link: just docs-check.
This guide The guide you read now lives in docs/guide/. It is a teaching layer on top of the docs. When the two disagree, the architecture docs win.

The writing style

The problem. The authors are mixed: the developer, many agents, and readers who may not be native English speakers. Long, clever sentences cause misreadings.

The rule is Simplified Technical English, light. It covers code comments, ADRs, concepts, commit messages and pull requests. The ten rules in short:

  1. One word, one meaning. The glossary is the dictionary.
  2. Short sentences. An instruction has 20 words or fewer. A description has 25 or fewer.
  3. One instruction per sentence.
  4. Active voice.
  5. Simple verb forms. Avoid “-ing” and perfect tenses where a simple form works.
  6. One topic per paragraph. Six sentences or fewer.
  7. Lists and tables for complex text.
  8. Plain words. “Use”, not “utilise”.
  9. Keep the articles. “the”, “a”, “this”.
  10. Warnings come first. Command first, then the risk.

Code comments: the last option

The problem. Comments rot. The code changes and the comment still says the old thing. A false comment is worse than none.

The rule. Write a comment only when it gives a fact that the code cannot show. A good name comes first. A comment is the last option. Five ideas hold the rest:

  • Comment the reason, not the action.
  • An interface comment gives facts: units, shapes, ranges, invariants, side effects, failure behaviour.
  • Point to durable sources: SUD-xx, ADR-NNN, a concept, a record in docs/research/. Never an issue or a pull request number.
  • No TODO, FIXME, XXX or HACK. Propose an issue. No commented-out code. Git keeps the old version.
  • Name the rule in every lint suppression, and give the reason in the same comment. Update or delete a comment when the code changes.

Test yourself. For each comment, decide: keep or delete?

/** The number of cells in a sudoku grid. */ above GRID_CELLS

It repeats the name. The code already says it. Rule 2: delete a comment that repeats the name or the types.

# SUD-10: training must never draw synthetic cells with this seed.

It gives a reason that the code cannot show, and it points to a durable rule, SUD-10.

// The spy comes before render: the worklet captures countFrame when it is created.

The test setup is not obvious. The comment explains why the order matters. It does not repeat the assertion.

// scan flow rewrite (issue #2) at the end of a component comment

Issues and pull requests belong in commits and pull request text. A comment points to a durable source, not to a ticket. just lint also bans TODO and blanket suppressions.

Risks and technical debt

The problem. Every project has weak spots. If nobody writes them down, they surprise you at the worst time. If they are written down, they are a plan.

Chapter 11 keeps two tables. A risk (R-nn) is a thing that may go wrong. It has an impact, a probability and a mitigation. A debt (TD-nn) is a shortcut that the project took on purpose. It names what will pay it off. Click a card to read more.

Click a card to read about it.

R-03: handwriting data is scarce

EMNIST does not look like pen in a printed cell, and own handwriting arrives slowly. Mitigation: heavy augmentation, the given / mine toggle in the correction screen, and the training-data export. A wrong kind is cheap to fix, because the player toggles it in one tap (ADR-006).

R-04: the real training data lives on one laptop

The image store is the only copy until DVC is adopted. Mitigation: back it up (Time Machine plus an off-site copy). The 2026-10-22 check found no backup on record. Never commit training images (SUD-08).

R-13: wrong labels in the data

About 0.6 % of the real cells have a wrong label. They cap the measured accuracy and teach the model mistakes. Mitigation: just suspects ranks the likely wrong labels. The “Doubtful labels” step of just label-cells is the check. The relabel and the retrain are still open (TD-01).

R-14: validation leaks

Cells cut from the same photo look alike. A random split puts near-twins in training and validation and flatters the numbers. Mitigation: split by page. The recent commit “split the real cells by sudoku page” (ADR-035) pays this off.

R-08: native-module upgrades break together

Expo SDK, VisionCamera, Skia, fast-opencv and fast-tflite must move in step. Mitigation: upgrade on a branch, all at once, with the ios-simulator workflow as the safety net. That workflow runs when a native input changes.

R-01: fast-opencv is young

One maintainer, no cornerSubPix. Mitigation: our own TypeScript computes the homography. The scanner interface lets one step move to Swift without touching the app (SUD-05).

R-15: misuse runs up the AWS bill

Mitigation (SUD-11): a stage throttle, a daily write count per player, bot protection, budget alerts and a kill switch. After the kill switch, just api-on <stage> turns a stage on again. See chapter 6.

R-07: scope creep on a side project

Backend, Android and a second model all look tempting. Mitigation: the order of work. The game ships first and is useful without the scanner.

TD-01: training on known wrong labels

Paid off by the review of the suspects, a relabel and a retrain.

TD-04: no promote gate

Today just install-model copies a model without fixture scores. This is the named exception to SUD-06. The future recipe is just promote-model. No issue exists yet.

TD-05: no fixture runner

No test runs the real scanner on fixture photos. This is why the pyramid layer 3 is a plan more than a daily tool. No issue exists yet.

TD-07: no pool of ready puzzles

On the iPhone, the slowest expert puzzles can take more than 1 s to generate. This touches QR-12. The iPhone check of #204 decides whether a pool is needed.

Why write debt down? “Debt taken on deliberately is recorded here with the ADR or issue that will pay it off.” A debt with no issue is marked “No issue yet”. A debt that the developer chose not to pay is marked “Not planned”. The debt stays known. A known shortcut is a decision. A hidden one is a bug waiting.

The iPhone build and the private model

The problem. The scanner needs a trained model. The model learned from photos that may not be published (SUD-08). So the model is not in git. A fresh clone plays every game, but its scanner has no model.

The steps for a first run on a device:

  1. just setup: install the TypeScript and Python dependencies.
  2. just train, then just export <run>, then just install-model <run>. The README points to ml/README.md for the details. In a new git worktree, run just install-model again, because the file is not in git.
  3. Find the device with xcrun devicectl list devices. Then run just ios-dev <UDID>.
  4. Start the Expo dev server with just app when the build needs Metro.

just bundle, just ios-measure and just ios-simulator all check first that the model file exists. They stop with the message “The model is missing. Run: just install-model <run>”.

Pitfall: two apps, two variants The development variant (just ios-dev) and the production variant (just ios-release) have different bundle IDs. The development variant talks to the development Clerk instance and the development sync API (ADR-022). Measure and test on the development variant. It also logs the [measure] lines.
Maestro, Java and the simulator

just e2e creates or finds the simulator “Sudoku E2E iOS 26”, installs the app and adds the fixture image shared/fixtures/imports/screenshot-digital.png to its photo library. It sets JAVA_HOME when Homebrew keeps Java keg-only. Pass one flow file, or flags such as --exclude-tags model. The flows clear the app data, so never point them at a simulator that you use every day.
